定位（README.md 原文）：「商品评价体系一期后端工程」，承接评价资格、商品评价、门店评价、首页待评价提醒、订单完成/退款事件消费、后管配置与统计等服务端能力。

这是本仓库群里工程规范最好的 Rust 项目之一
  • 严格的 DDD 分层：domain（模型/状态机/不变量）→ app（用例/DTO/Repository trait/消息抽象）→ infra（MySQL/Redis/RocketMQ/配置/ID 实现），依赖方向清晰且 Repository 以 trait 定义在 app 层、实现在 infra 层（依赖倒置）。
  • 单一终态 DDL：sql/ 明确标注「人工执行的唯一终态 DDL」，避免了其它仓中 migration 散乱的问题。
  • docs/ 齐备：技术方案、工程规范、任务拆解、资源清单分目录维护。
  • 一个二进制多形态：review-worker 通过 WorkerApp::resolve(mode, app) 解析出 7 种角色，与 gitops 的 7 个 worker 服务一一对应——部署单元与代码形态显式对齐。

02部署形态与 worker 一个二进制 7 种角色

WorkerApp 变体职责对应 gitops 服务
OrderConsumer消费订单完成/退款事件，生成评价资格review-order-consumer
ExpireWorker评价资格过期处理review-expire
EventPublisher领域事件外发review-event-publisher
StatWorker评价统计聚合（StatsConsumer / OnStatsProcessed）review-stat
CompensationWorker补偿任务review-compensation
RiskWorker风控事件处理review-risk
NotifyWorker待评提醒通知（NotifyScheduleMessageHandler + AsyncNotifySchedulePublisher）review-notify

加上两个 HTTP 服务 review-c（C 端）与 review-b（后管），恰好对应 gitops retail-review 命名空间中的 review-b / review-c + 8 个 worker 的服务清单。

可开关的功能位 代码中有多处显式开关，便于分阶段上线：worker.execution_enabled、notification.schedule_mq_publish_enabled、schedule_publish_concurrency。启用通知消费时会强制校验 rocketmq.notify 配置存在（enabled notify schedule consumption requires rocketmq.notify config）——fail-fast 而非静默降级，这一点比同期其它仓做得好。

  • 标签体系：/admin/review/tags（+ /list//detail//update//delete）、/tag-categories

需确认 C 端存在一个 /test 端点，建议确认其在生产是否可达（同类问题在其它仓已构成风险，参见 11 篇的白名单放行 test/**）。另本次未核验两个服务的鉴权装配方式，属待复核项。

图 2 · 评价状态机（ReviewStatus：None=0 / Partial=1 / Done=2 / Expired=3 / Canceled=4）

状态枚举通过自定义宏 impl_tinyint_enum! 生成与 tinyint 的双向映射（review-domain/src/status.rs:39-51）——把 DB 编码与领域枚举的映射收敛到一处，避免了其它仓中「枚举 code 重复 / fromCode 返回 null」那类问题。

领域层还包含 order_fact.rs（订单事实，用于从订单事件推导评价资格）、quantity.rs（数量值对象）、qualification/（资格子域）——值对象与不变量下沉到 domain，是标准的 DDD 做法。

06观察与风险 本次为首轮分析，深度有限

核验范围说明 本篇是在有限预算内完成的首轮结构性分析：已确认分层、crate 职责、部署形态、路由清单、表清单、状态机。尚未逐文件核验以下内容，列为待办：

待复核清单

  • 鉴权：review-c 与 review-b 的鉴权中间件实现；后管 11 个写接口是否有权限校验；/test 端点在生产的可达性。
  • 凭据：配置文件与 .env 中是否有明文凭据入库（本次未定位到 config/*.toml，需确认配置加载方式）。
  • 并发正确性：评价提交的幂等（同一订单重复提交）、review_stat_* 统计聚合是否为原子操作或存在读改写竞态、资格生成与过期的并发处理。
  • panic 路径：请求路径上的 unwrap()/expect()/数组下标；Cargo.toml 的 panic 策略（对比 icc-task 用 abort 会导致 pod 被杀）。
  • MQ 语义：RocketMqSimpleConsumer 的 ack/重试/死信策略；EventPublisher 是否有 outbox（本仓有独立的 event-publisher worker，看起来正是 outbox 模式，值得确认——若成立，这是全平台少见的正确做法）。
  • 风控逻辑：RiskWorker 的判定规则与 review_risk_event 的处置闭环。
  • 导出：后管导出接口是否有分页/行数上限（同类问题在 icc-task 构成 High 风险）。
初步判断 从结构、命名、分层、开关设计、fail-fast 校验、独立审计与风控表来看，该仓的工程成熟度显著高于平台内其它 Rust 服务（对比 12 篇中普遍存在的鉴权缺失、明文凭据、panic 路径问题）。若上述待复核项也无重大缺陷，可作为平台内 Rust 服务的参考实现。
