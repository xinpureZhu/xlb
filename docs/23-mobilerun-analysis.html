01定位与版本状态 开源 Agent 框架 · 闭源设备驱动 · 0.6.x 早期版本

mobilerun（原 droidrun）是一个用 LLM 直接操作手机的框架：把设备 UI（无障碍树 + 截图）喂给大模型，由模型产出 click/type/swipe/open_app 等原子动作，循环执行直到任务完成。它不是测试框架（没有断言、没有用例 DSL），而是一个「手机操作 Agent 运行时」；可用的入口是 CLI、Python SDK 与 Docker。

四个设计决定值得注意：① 编排用 llama-index Workflow，所有环节以 Pydantic 事件（ManagerPlanEvent、ExecutorResultEvent、ToolExecutionEvent、ResultEvent…）串联，因此外部可以 stream_events() 实时接事件做 UI、用量统计与日志。② 跨代理协作不走消息传递，而是共用一个 MobileAgentState（plan、current_subgoal、agent_memory、action_history、error_flag_plan…），这也是它能把「规划-执行-复盘」串成闭环的基础。③ 工具注册表是唯一真相源，工具自带 deps 能力标签，装配时按驱动与状态提供者声明的能力集过滤（disable_unsupported）——同一份 prompt 在 Android 与 iOS 上看到不同的工具表。④ 提示词是 Jinja2 模板（config/prompts/{fast_agent,manager,executor}/*.jinja2），可通过 MobileAgent(prompts={...}) 只覆盖字符串，不改代码。

架构边界：mobilerun/ 只是 Agent 框架，不含任何驱动实现；DeviceDriver/AndroidDriver/IOSDriver/CloudDriver 全部来自 PyPI 包 mobilerun-core-local（其 GitHub 仓库 droidrun/mobilerun-core-local 与 droidrun/mobilerun-core 均返回 404，即仓库不公开，只有 wheel 可读）。审计与可控性只能止步于 wheel 内的纯 Python 源码，设备协议细节不受本仓控制。

03两种模式与控制循环 direct = XML 工具循环 · reasoning = 规划 + 单步执行闭环

Areasoning=False · FastAgent

ReAct 循环：Thought → Tool Call → Observation。模型必须以 <function_calls><invoke name=…><parameter name=…> 的 XML 协议发起工具调用，框架解析后把结果包成 <function_results> 回灌为一条 user 消息。没有规划层，适合「截图、发消息、开关设置」这类单步或短链任务。

健壮性：连续 3 次 XML 不可解析即终止（_MALFORMED_TOOL_CALL_LIMIT），中途注入纠正提示；同一响应里的相邻重复调用块会被丢弃。

Breasoning=True · Manager + Executor

Manager 出 <plan> 与 current_subgoal，Executor 只做一步动作并回报 ### Thought / ### Action / ### Description，随后 Manager 在拿到新 UI 状态后重新规划（而非一次规划到底）。Manager 有 stateful（带 message_history）与 stateless（每轮重建 prompt、只取最近 5 条动作历史）两实现。

纠错：执行错误连续达 err_to_manager_thresh（默认 2）即置 error_flag_plan，把错误升级进 Manager 的规划上下文；Manager 响应契约校验失败最多重试 3 次。

图 4 · 四条接入路径：本地 ADB+Portal / 纯视觉远端 / iOS HTTP / 云端托管

1Android Portal

设备端安装 com.mobilerun.portal，注册无障碍服务 …service.MobilerunAccessibilityService。mobilerun setup 完成「装 APK + 开无障碍」两步；mobilerun ping 校验通道（TCP 或 content provider 两种）。

纯 HTTP 模式下驱动要求非空 bearer token（AndroidDriver 的 HTTP 变体），示例端点 http://127.0.0.1:8080；use_tcp=True 时由 PortalClient 做 localhost:N → device:8080 端口转发。

2iOS：两套并存（新 portal-http / 旧 ios-portal）

框架里 iOS 有两个驱动类：IOSPortalHttpDriver（新，与 Android Portal 同一套 HTTP 契约）与 IOSPortalDriver（旧 ios-portal，GET /device/date 探测，已归档但驱动仍在）。create_ios_driver() 会先探测再选：/ping 返回 pong 且 /version 结果以 iosportal( 开头 → 新链路；否则退回旧链路。

能力差异很大：新链路 supported = 基类全集 ∪ {get_date, install_app}（含 get_apps/list_packages/stop_app/press_key_code），按键支持 {home, back, enter, delete, app_switch}；旧链路只有 8 个动词、按键仅 {home}，install_app/uninstall_app/stop_app/press_key_code 明确不支持。官方 SDK 文档描述的是旧链路，故其「iOS 只支持 home / 不能枚举 App」的说法对新链路已过时（见 §7）。

3云端设备

CloudDriver(device_id, api_key)，默认 https://api.mobilerun.ai/v1；key 取 MOBILERUN_CLOUD_API_KEY 或凭据文件；传 UUID 形状的设备号会自动路由到云。Portal 侧还有一条反向连接开关（configure_reverse_connection），示例地址解出为 wss://api.mobilerun.ai/v1/providers/personal/join——即自有手机也能被云端反向接管。

云定价公开：自带机 $5/月/设备、独立 Android 机 $80/月、iPhone $200/月（需 on request）、按量 $0.03/设备分钟、agent step $0.01（1 credit = 100 steps）；无免费额度，小字声明 SOC 2 仍在路线图。

iOS 实现链路（本次逐层落到 wheel 源码）：与 Android「装一个 Portal APK」不同，iOS 侧是宿主侧桥 + 设备端 XCTest agent：设备上跑的是 WebDriverAgent（XCTest 进程），由 macOS 上的 mobilerun-ios 拉起并以与 Android Portal 相同的 HTTP 契约对外暴露，框架只认这个 HTTP 面。

iOS 的三个硬门槛：① mobilerun-ios 是闭源二进制（README 明说源码在私有仓库，仅在本仓发 release + SHA256SUMS），且仍是 0.5.0-rc.* 预发布；② 需要 macOS + Xcode + 可签名 Apple ID，每次 WDA 重签都要走一遍；③ 旧链路的状态来源是「把 XCTest 调试文本用正则拆成树」（源码自述「No filter/formatter pipeline」「normalized coordinates untested on iOS」），属于明确的脆弱点——能用新链路就别用 legacy。

对内部选型的一句话结论：iOS 侧 mobilerun 的形态是「宿主侧桥 + XCTest agent + 与 Android 同构的 HTTP 契约」，Android 侧的成熟度（Portal 0.7.25、权限与端口都定型）明显高于 iOS（RC 二进制、依赖 Mac 与签名、双链路并存）。若只做 Android，iOS 这些复杂度可以先不计入成本。

可靠性自愈：状态读取 fetch_state_with_retry 默认 7 次尝试、退避 [1,2,3,5,8,10] 秒，第 5 次失败后调用 _recover_portal()（重启无障碍服务，必要时重启 Portal socket server 并刷新 token）——说明「无障碍服务被系统杀掉/掉线」是这套方案的常态化故障，即为 Android 自动化的固有成本。
Portal 的权限面远大于「UI 自动化工具」（企业合规必查）：清单含 SYSTEM_ALERT_WINDOW（悬浮窗）、MANAGE_EXTERNAL_STORAGE（全盘存储）、RECEIVE_SMS（读短信）、READ_CONTACTS、REQUEST_INSTALL_PACKAGES（可装包/自更新）、usesCleartextTraffic="true"，并实现无障碍服务、通知监听、自定义输入法（MobilerunKeyboardIME）、屏幕投屏（mediaProjection）、开机/短信触发器与导出型 MobilerunContentProvider。换言之：装了它，等于把设备交给一个系统级 Agent。
供应链与控制点：Portal APK 只从 GitHub Releases 分发（无应用商店），最近版本 v0.7.25 资产约 53.6 MB（附 sha256），构建签名使用仓库 CI secrets，非可复现构建。框架 mobilerun setup 在运行时自动下载安装（release 查询先 api.github.com、失败回退 ungh.cc）。落地上两条硬要求：① 隔离环境必须自带 APK（setup --path）并校验 sha256；② 固定 Portal 版本（上游 release notes 明确「pins Android Portal compatibility to 0.7.25」，版本漂移即断配）。

06配置、可观测性与成本 5 个 LLM 槽位 · 遥测默认开 · 轨迹三档 · 成本可配但不可控

1LLM 配置与 Provider

5 个可插拔槽位：manager、executor、fast_agent、app_opener、structured_output；默认全部 GoogleGenAI，温度分别 0.2/0.1/0.2/0.0/0.0。_get_required_profiles 按模式只要求其中若干项：reasoning 需 manager+executor+app_opener，direct 需 fast_agent+app_opener，带 output_model 再加 structured_output。

运行时 provider：OpenAIResponses / OpenAILike / GoogleGenAI / Ollama / Anthropic / DeepSeek / OpenRouter / MiniMax / XAI，另有 4 类 OAuth 运行时；Anthropic 需额外 extras。

2凭据与配置落盘

设备凭据由 credential_manager 管理，agent 只见 secret_id，写入走 type_secret。但 LLM provider 的 API key 是明文存在 credentials/auth-profiles.json 的 apiKeys.<provider>；api_key_source="auto" 时该文件优先于 shell 环境变量。

配置目录沿用旧名 droidrun（macOS ~/Library/Application Support/droidrun/config.yaml），文件权限 0o600，_version: 7，配 config_manager/migrations/v002…v007 自动升级；credentials.enabled 只管设备密钥，不管 provider 认证。

3可观测性

tracing：Phoenix（默认，localhost:6006）或 Langfuse，能看到每次 LLM 调用、Manager/Executor 工作流与工具结果。trajectory：none（默认）/ step / action 三档，落盘到工作目录 trajectories/，含每步截图、无障碍树、动作与推理；官方用途明确包含「构建训练数据集」。macro：录制后的轨迹可用 mobilerun macro replay 回放，带 --state-threshold 0.85 状态匹配与 --on-mismatch stop|agent。

4遥测与成本

遥测默认开启：PostHog（HOST=https://eu.i.posthog.com，disable_geoip=False），匿名 ID 持久化在 ~/.droidrun/user_id；上报字段里 MobileAgentInitEvent.goal 是用户原始自然语言任务文本，另有 visited package/activity、成功与步数。三种关闭方式任一显式 false 即生效：TelemetryConfig(enabled=False) / YAML / MOBILERUN_TELEMETRY_ENABLED=false（旧名 DROIDRUN_TELEMETRY_ENABLED 仍兼容）。三条链路的边界清晰：遥测出网、tracing 出网到自建 Phoenix 或 Langfuse、轨迹只留本机。

成本：vision 会显著抬高 token（截图入 prompt）；官方给出的省钱配方是 --provider GoogleGenAI --model gemini-3.5-flash-lite --no-vision。第三方实测最省任务集下 $0.075 / 3,225 tokens / 任务（见 §8），失败重试与长链任务会成倍放大。

08评估：能力、局限与风险 榜单 91.4% vs 第三方 43% · 概率性操作不适合无值守生产

A官方口径（自报，未经独立验证）

AndroidWorld 116 个任务、91.4%（106/116），由官方 blog 与官网 benchmark 页发布（2025-10 首次公布 91.4%，此前 63.0% → 78.4%），方法自述为 Manager–Executor 动态反馈环 + 八动作原语 + 六项工程改进。

但口径要打折：① AndroidWorld 官方 leaderboard 首页即声明「Community-submitted results. No independent verification is performed.」；② 该榜上 DroidRun 的 91.4 记录 Number of trials = 1，且被后来的条目（如 FluizAI 100.0、Artemis 99.1，均 1 trial）超过；③ 同榜 人类基线 = 80.0（3 trials），即分数已超过人类平均；④ 榜单记录的配置是「Screenshot + A11y tree」，与官网宣传的「direct accessibility API」不一致；⑤ 评测代码仓 mobilerun-android-world 已近一年未更新。

相关学术工作 WWW '26 论文（arXiv:2601.19306，「Curiosity Driven Knowledge Retrieval for Mobile Agents」）在其配置下报告 88.8%（GPT-5 + AppCards），称优于此前最好 84.5%；但作者含该公司员工与联合创始人，属同一方结果，不是独立复现。

B第三方实测

AIMultiple（2026-06-09，更新版）在 Android 模拟器上用 65 个真实任务横评四个 agent：DroidRun 43% 成功率（最高），Mobile-Agent 29%，AutoDroid 14%，AppAgent 7%。

同集最省任务上 DroidRun $0.075 / 约 3,225 tokens / 任务、耗时 78s；AutoDroid 57s、$0.017 最快最省；AppAgent 最贵（$0.90）最低效。

把两个数字放在一起看：榜单 91.4%（自报、1 trial、无独立验证）与真实任务 43% 的巨大落差，本质是基准可解性与真实 App 复杂度的落差——AndroidWorld 以系统 App 与固定任务为主，而真实业务 App 有 WebView、自绘 UI、弹窗、风控与登录态。评估任何移动 Agent 时，必须以「你自己 App 上的实测成功率」为唯一准入依据；厂商榜单只能用来筛掉明显不合格的方案。
