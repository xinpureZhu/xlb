05修改环境变量：两条路径审批式为正式路径 · 调试式无鉴权且绕过审批

「修改服务环境变量」不是单个接口调用。microservice 模块提供两条互不相同的路径：

01审批式（正式路径）

updateMicroServiceConfig 直接打 patch，不经审批、无鉴权。源码注释写明「调试用」。不应作为常规手段，且需评估是否应从 pubRouter 移除。

环境变量的路径格式——这是此前源码推不出、现由实测确定的关键结论：

读（getMicroServiceConfigById 返回体）里，环境变量是嵌套 JSON：

serviceConfig.envs.<变量名>                    # 标量：所有环境同值
serviceConfig.envs.<变量名>.<环境键>          # 对象：按环境分组

返回体里 <环境键>是逗号拼接的环境组合字符串（如 prod,prod-gray），不是单个环境。实测 60 个 key 的环境键组合分布：

环境键组合key 数量
staging,staging-gray + test,test-gray（无 prod）13
prod,prod-gray + staging,staging-gray + test,test-gray12
default + staging,staging-gray4
staging + test,test-gray / default,test,test-gray 等3
标量（无环境维度，所有环境同值）约 28
写格式已由真实请求确认（走增量 createMsUpdateConfigApproval）。写与读的路径写法不同：读是点分嵌套 serviceConfig.envs.X.Y，写是扁平路径字符串，用 ` > ` 分隔（空格-大于号-空格），value 为 {环境键: 新值} 对象： 
POST /efficiency/microservice/createMsUpdateConfigApproval
{
  "id": "<configId>",
  "versionId": "<来自 getMicroServiceConfigById 的乐观锁>",
  "patchData": {
    "add": {},
    "update": { "envs > COMPANY_ID": { "staging-gray": "4301" } },
    "delete": []
  }
}
要点：① 路径前缀是 envs 而非 serviceConfig.envs；② 分隔符是 > 而非点号；③ 环境键这里用单值 staging-gray（COMPANY_ID 本就按单环境存），改组合环境的变量时环境键写法仍建议先读返回体对齐；④ versionId 必带，用掉后会刷新，界面里的旧值随之失效。
此写法为静态观察所得，未实际提交。提交该请求会创建一条真实飞书审批单并消耗 versionId，按仓库只读约定不代为执行。全量修改另走 createMsFullUpdateConfigApproval（传 rawJSON 完整配置）。
安全发现：serviceConfig.envs 中 *__PASSWORD / *__SECRET / *__KAFKA__PASSWORD 等敏感项的值以明文形式存储并由该接口直接返回（本节已全程脱敏未记录任何值）。与其他仓库的明文凭据问题一致，建议纳入统一整改：敏感项改用 secretKeyRef 引用，避免出现在配置查询响应里。
serviceYaml.envs 为空而 serviceConfig.envs 有 60 项——两个 envs 字段并存。serviceConfig 是当前实际生效的配置，serviceYaml 疑为 v2 迁移中的新结构占位。改配置应作用于 serviceConfig.envs；若 SOP 指向 serviceYaml，需先确认迁移状态，否则 patch 打空。
