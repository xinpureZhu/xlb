02平台定位与整体架构控制面自研 · 调度面是 ATE · 隔离靠 runsc 而非 RuntimeClass

Agent Square 是一个多 Runtime 的 AI Agent 托管平台。它把每个「用户 × Agent」建模成一个 Actor，Actor 在 gVisor 沙箱里执行， 并通过 挂起 / 恢复 复用到一组数量有限的 Worker Pod 上。调度控制面在代码与部署里的真名是 ATE（ate-api-server / ate-controller / atelet / ateom-gvisor），仓库文档里称之为 Substrate。

之所以是哈希而不是可读结构，是因为 Substrate 只接受 DNS-1123 label（≤63 字符）。设计 ADR 里规定的 <tenant>/<agent-name>/<scope-id> 形式并未落地。租户维度目前恒为 default，属遗留兼容，平台没有多租户。

多路复用：代码验证（substrate 8ec057de）

机制部分已由 substrate 源码验证（下述引文均出自该仓）。仍属 设计文档 的只有三份 Draft Actor ADR 的验收条件 （coldStartSupported、preSuspendHook、multiplicityHint、pkg/state/ SDK、5 万 Actor 压测），尚未满足，不可当作已交付能力。

复用是时间维度的，已验证：Worker 记录只有一个 actor_id 字段，ateom 用单把 sync.Mutex 串行化全部 RPC， 即一个 Worker Pod 同一时刻只服务一个 Actor、沙箱内单进程串行。状态机与旧文不同——没有 CREATED 状态： CreateActor 直接写 STATUS_SUSPENDED，枚举为 SUSPENDED → RESUMING → RUNNING → SUSPENDING → SUSPENDED，四个迁移全部在 ateapi 的工作流引擎里同步执行。

substrate pkg/proto/ateapipb/ateapi.proto:58-64 · cmd/ateapi/internal/controlapi/create_actor.go:43-49 · workflow_resume.go:143-159,:469-485 · workflow_suspend.go:85-126,:269-397 · cmd/ateom-gvisor/main.go:155-156

「每 Actor 一把互斥锁」在调度面侧的实现是分布式 Redis 锁而非进程内 mutex：键 lock:actor:<id>、SET NX、 TTL 300s，工作流上下文 298s；并发操作直接收到 gRPC Aborted。恢复顺序验证为 Actor LastSnapshot → ActorTemplate GoldenSnapshot → 冷启动 Run，含损坏快照检测；恢复失败会把 Actor 回滚到 SUSPENDED 并释放 Worker。 Golden 快照也不是文档说的「临时 Golden Pod」：atecontroller 建一个 golden actor，在普通 worker 上 resume、等 20s、再 suspend。

substrate cmd/ateapi/internal/workflow/workflow.go:58-93,:188-189,:322,:353-376 · workflow_resume.go:257-430,:439-459 · internal/controllers/actortemplate_controller.go:70-150

设计文档 容量公式 WorkerPool 容量 = RUNNING × 峰值系数 3；示例测算 5 万 Actor、约 1000 并发 RUNNING 对应 30–60 个 Worker Pod。 已知故障模式是卡在 STATUS_SUSPENDING；某次事故记录中跨 CPU FeatureSet 的快照恢复失败率达 23.5%，这也是部署脚本拒绝变更 WorkerPool 节点亲和的原因。

直连路径：atenet 的 DNS + Envoy 跳转

除第 03 节的 pod-exec 控制路径外，Actor 自身暴露的 HTTP 服务走另一条已验证链路：CoreDNS 把 <actorID>.actors.resources.substrate.ate.dev 的所有名字答成 atenet-router 的 ClusterIP； Envoy ext_proc 从 Host 解析 Actor ID，singleflight 调 ResumeActor（MaxWaitMs=120000）， 再把 :authority 改写成 workerIP:80 放行。注意这条路径无任何认证（见风险表）。

吞吐现状：两侧瓶颈不同

消费侧（第 10 节矛盾 14 已修正）：派发循环单 goroutine、单批 10，但每任务独立 goroutine，串行来自每用户泳道默认 1。 调度面侧没有派发队列：每个 ResumeActor 是同步 RPC，阻塞在快照下载 + runsc restore 上， 吞吐上限 = Worker 数 × 单次恢复延迟；每次 assign 还要全量扫一遍 Worker 列表。与 505 任务 / 1342s 的压测数字（约 2.66s/任务）不矛盾， 但压测 harness 在 benchmarking/locust，结论仍以消费侧日志为准。

mcp-proxy 为什么必须存在

Actor 绝不能持有上游凭证，也不能通过工具参数自选服务 / URL / 工具。网关把这三件事都收进服务端：

  • 唯一公开面 POST /{routing_key}/mcp，裸 /mcp 直接 404；无对外路由，仅集群内 mcp-proxy.<ns>.svc.cluster.local:8080 可达。
  • 不持久化任何凭证：每次调用向 Go 控制面 POST /internal/mcp/v1/resolve 取，缓存 ≤30 秒，按 binding/user/auth_version 分键，失败即 fail-closed。
  • ES256 Binding JWT 对 JWKS 校验，强制 kid、issuer、aud=mcp-gateway，并校验 URL 段与签名内 routing_key 相等。
  • MongoDB 为权威源（mcp_services / mcp_service_revisions / agent_mcp_bindings），30 秒原子快照刷新；binding 指向已停用服务或未发布工具时整体 fail-closed。
  • 超时 2s/5s/10s 且无自动重试；请求体 1MiB、响应 4MiB 上限；禁重定向、trust_env=False、SSRF 出网白名单。

当前指针所在分支 feat/multi-ack 的实质是引入可选 auth_session_id 声明，把「当前登录用户」这类会话型凭证按会话分键， 使多个并发用户会话不共用同一个上游 MCP 客户端。该改动已包含在 main 中（指针落后 main 3 个提交）。
