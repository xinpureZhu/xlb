H7 Node AuthGuard 只在 APP=pc-bff|pc-bff-gray 时注册，而业务模块在所有角色加载 仍是条件注册：if (['pc-bff','pc-bff-gray'].includes(APP)) 才 push APP_GUARD（app.module.ts:132-140）。 仍存在

核心结论未变：Node 仍不可下线 两项 🔴 阻塞缺口（库存 TCC 引擎与 ChangeStream 驱动的 OSS 分发）在这一轮迭代中都没有迁移。Java 侧的扩张集中在新增渠道与同步链路（自营外卖事件/库存同步、MPS 门店同步、C 端、补贴），而非承接 Node 的核心能力。

换言之：两代并行的时间还会延长，而并行期的一致性责任仍全部压在应用层（无跨集合事务、无跨代锁）。

正向进展 Node 把内嵌的 Lua 脚本抽成了 src/redis/lua/*.lua 独立文件——这让库存 TCC 的原子操作可读、可测、可复用，也为将来迁移到 Java 降低了移植难度（脚本本身与语言无关）。

00核心结论 数据面完全共享 · Java 暂不能独立部署

#结论关键证据
1两代共用同一套 MongoDB / Redis / ES / Kafka 集群，不是独立数据面环境变量名逐字相同；Java 固定库名 goods；14 个集合名与字段名逐字相同
2Java 无法独立部署——库存同步强依赖 Node 仍在运行Java 把 ERP 库存推到 erp_stock topic，唯一消费者是 Node
3库存 TCC 引擎完全未迁移（本服务最核心能力）Node 侧 try/confirm/cancel/refund + 16 个 Lua 脚本；Java 侧无 /inventory 控制器，InventoryServiceImpl 仅 81 行 1 个方法
4Node 的 Mongo ChangeStream 会被 Java 的写入触发（隐式跨代耦合，当前实际有益）Node 3 处 .watch()；Java 全仓 0 处 ChangeStream
5ES 同步 topic 名两边不一致 → Java ES 消费者收不到 goods-b 的消息生产端用环境变量，Java 消费端硬编码了另一个 topic 名
6两侧都有未鉴权的高危写接口Java 白名单放行 dataClean/**、test/**、api/**；Node 的 sendMessage 可向任意 topic 注入任意消息
7Node 的 AuthGuard 只在特定角色注册，而业务 Module 在所有角色都加载app.module.ts:131-136 vs :98-111
结论 两代技术上可以并行运行（数据面共享），但代价是所有一致性责任落在应用层——无跨集合事务、无跨代锁。而「Node 下线」当前不可行，被 4 项 🔴 缺口阻塞（详见 §08）。

02Node 版结构 按 APP 角色分裂部署 · 承载 TCC 与 ChangeStream

Node 版通过 APP 环境变量切换部署角色（pc-bff / 各同步 worker），同一镜像跑不同职责：

  • 业务模块：product(+storeProduct/import)、catalog、category、homeSearch、inventory、label、tag、store(+report)、settings、oss、health。
  • 同步作业 data_transmission/：erp_stock_sync、erp_store_sync、official_product_sync、opStoreProductRelation、dfp_sync、task。
  • ChangeStream 订阅者 subscriber/：product / inventory / store 三处 .watch()，驱动积分商城 JSON、tag、homeSearch 等 OSS 产物重建。
  • 后台 worker：store-product-summary.worker（60s 间隔）+ dirty-rebuild。
鉴权装配缺陷 AuthGuard 仅在 APP=pc-bff|pc-bff-gray 时注册（app.module.ts:131-136），而 imports（含 InventoryModule/ProductModule）在所有角色都加载（:98-111）→ 以 worker 角色启动的实例暴露了全部业务接口且无鉴权。

03数据面共享性判定 同库同集合 · Java 主动做了兼容适配

判定为「共享同一数据面」的硬证据：

  1. 连接串来自同名环境变量（RETAIL_BFF__GOODS_MONGODB__URL 等）。
  2. Java 固定库名 goods；集合名与字段名逐字相同。
  3. Java MongoDBConfig 显式 setTypeMapper(new DefaultMongoTypeMapper(null)) 关闭 _class 字段——正是为了与 Node 写入的文档兼容。
  4. Java 有 StringToLocalDateTimeConverter，注释写「兼容数据库时间字段出现脏数据，时间字段变成了 string 类型」——证明在读 Node 写入的历史脏数据。

04Kafka 拓扑与 ES 写入分裂 无双消费 · 但 ES 路径被劈成两条

Node 的 group 命名是 groupId = topic，Java 是 <topic>_group——同一 topic 上两代 group 必然不同，所以若同时监听必然双消费。逐 topic 核对后结论：当前配置下不存在同一 topic 被两代同时消费。

真正的风险来自反面——topic 名分裂导致消息投递到错误管道：

06接口契约兼容性 字段名兼容做到了 · 外层信封已漂移

README 声称「为减少前端改动，对外接口字段保持和 node 项目一致，都是非驼峰命名」。源码验证通过：

  • DTO 字段名本身就是 snake_case（不是靠注解映射）：store_id、image_url、product_type、store_stock、channel_sale_status、sku_id… 与 Node 对端逐字一致。
  • 分页包装体是加性扩展：Java 保留 total_elements/total_pages/content，另加 pageNo/pageSize → 向后兼容 ✅。
  • 序列化链路：FastJson2 converter 被插到 converters 第 0 位，接管所有 JSON 输出且不做命名策略转换。
两个隐患
  • Jackson 埋伏：配置里同时有 spring.jackson.property-naming-strategy: SNAKE_CASE，当前被 FastJson 覆盖而无效；且有一行被注释掉的「移除 Jackson converter」代码。若某天 FastJson converter 被移除或降级，Jackson 会接管并把 pageNo → page_no、traceId → trace_id，响应契约瞬间破裂。
  • 外层信封已漂移：msg 字段 Node 是 '请求成功'，Java 是 'success'。前端若断言中文文案会失败。Java 另加了 success/traceId/spanId。

07风险清单（分级） 两代同病：库存读改写无锁

Critical

  • C1 明文凭据入库（含生产密码）：Node 的 .env.local/.env.test 未被 gitignore 且已提交，含 test 与 prod 两套 Redis 密码、固定 JWT_SECRET、ES 主备、Kafka SASL、OSS AK+SK、ERP MDM SERVER_TOKEN、飞书 webhook。Java 侧 7 个模块各有一份 application-local.yaml，含 Kafka/Redis/Mongo 密码与 mdmToken 默认值。修复必须包含轮转全部凭据，删文件不够。

High

1H1 库存读改写无锁 → lost update

两代同病，且共享同一份数据 → 跨代并发同样丢更新。

08Node 下线前置条件 P0 止血 → P1 一致性 → P3 补齐缺口

P0（立即）

  1. 轮转 .env.local/.env.test/application-local.yaml 中全部凭据并清理 git 历史；.gitignore 加 .env*、application-local.yaml。
  2. 删除 Java 白名单中的 dataClean/** 与 test/**；给 api/** 加内网鉴权；生产关闭 knife4j。
  3. 给 Node 的 sendMessage 加鉴权 + topic 白名单 + prod 保护。
  4. Node AuthGuard 改为无条件注册，或按角色裁剪 imports。
  5. 修复消费者异常吞掉的问题（异常必须外抛）并落地 DLQ。
  6. 统一 goods_official_product_sync topic 名，消除 ES 写入分裂。

P1（一致性）

  1. 库存链路引入分布式锁（RedisLock.executeWithLock("{store}:{sku}")）或改用 Mongo $inc + 乐观锁；跨代锁必须统一 key 前缀。
  2. 把 Redis 写移出 Mongo 事务（改 afterCommit），并加缓存重建兜底。
  3. ES 备集群写入改同步 + 失败落 outbox + 重试。
  4. Java 实体补齐索引注解（至少 product.sku_id、store_product_relation.(store_id,sku_id)、inventory.(store_id,sku_id)）并纳入启动校验。
  5. 批量关联接口的上限从 400 万降到可控值；Excel 导入改分批 + 行数上限；导出改流式分页。

P3（决定 Node 能否真正下线）

排期迁移 G1–G4：库存 TCC 引擎、ChangeStream 副作用、两个 ERP 同步角色、DLQ 与消费者自愈。这四项完成前，Node 不可下线。

并行期注意 Node 的 ChangeStream 目前会被 Java 的写入触发，从而自动重建 OSS 产物——这是「期望之外但当前有益」的桥接。反过来说，Node 一旦下线，这些副作用会静默消失，不会有任何报错提示。
