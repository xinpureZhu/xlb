02member-service 架构与接口面 api → deps → services → repositories → models 严格单向，Session 全层透传

技术栈：Python ≥3.12、FastAPI（同步路由）、SQLAlchemy 2.x（Mapped 声明式）、PyMySQL、Pydantic v2 + pydantic-settings、uv 管理依赖。 入口 app/main.py:17-30：注册 5 个 router（前缀 /api/v1）+ BizError 全局处理器 + GET /health。 DB 引擎/会话工厂惰性创建（app/db.py:14-26），无 Alembic —— schema 以 docs/sql/member-schema.md 为准手工建表，集成测试直接解析该文档的 CREATE TABLE 建库（顺带验证 DDL 文档可重放）。

一个关键设计：所有路由的服务装配都写 Depends(get_session, scope="function")（app/api/deps.py:55,66,79,94,115,136,148）。 这是评审记录 CR #8 的修复点——默认的 yield 依赖会在响应发送之后才 commit，存在「客户端已收到 2xx、事务却没提交」的窗口；改成 scope="function" 让提交先于响应。

鉴权现状（评审已记录、需求方已决策接受）：全站没有认证授权。身份取自可伪造请求头 X-Operator-Type（默认 2=MEMBER）/ X-Operator-Id（默认空，app/api/deps.py:34-44）； 5 个 admin 路由无角色校验；路径 member_id 无归属校验（IDOR）； /admin/cancel-applies/execute-due 连 operator 依赖都没有（app/api/v1/admin.py:57-60），审计里 operator_id 恒空。 成立前提是「仅内网部署、仅可信内部服务可达、不直接对 C 端开放」；对 C 端开放或接统一登录时必须补齐。

03资产变动的资损防线 幂等键 + savepoint + 行锁 + 场景符号校验，四道防线是这仓最扎实的部分

资损面集中在 POST /members/{id}/asset-changes，防线按顺序叠了四层（app/services/asset_service.py）：

1幂等键

唯一索引 uk_biz_asset (biz_no, asset_type, asset_ref_id)；账户型 asset_ref_id 强制 0、卡类必须 >0，键各段全由服务端决定。

2命中即校验

幂等命中后比对 member / 场景 / 金额符号，不一致返回 409 IDEMPOTENCY_CONFLICT（避免「退款被吞」）。

3savepoint 兜底

并发撞唯一键时用 begin_nested() 只回滚流水插入，不丢弃调用方（审批单）未提交状态。

4行锁 + 非负

余额/卡更新走 with_for_update()；after < 0 直接 409 INSUFFICIENT_BALANCE；DDL 另有 CHECK 兜底。

图 2 · 资产变动调用时序：预检幂等 → 行锁 → savepoint 兜底 → 同事务提交

隐性不变式（读码推断，未在此环境验证）：幂等路径的正确性依赖「余额/卡余额的 UPDATE 被 flush 在 begin_nested() 之内」（asset_service.py:117-127，flow_repo.add() 触发 flush）。 冲突时 savepoint 连带回滚这笔余额改动、并由 SQLAlchemy 让对象失效，于是重复请求不会二次加钱。 一旦有人把流水插入的 flush 挪到 savepoint 之外，重复请求就会真的重复加扣。建议补一条并发重复请求的集成测试，把这个前提钉死。

其他已修的关键点（来自评审记录）：单轮无盐 sha256 → pbkdf2_hmac + 每用户盐（register_service.py:28-31）；金额入参 Field(max_digits=16, decimal_places=2) + 积分整数校验；响应金额一律经 dto.money() 输出两位小数字符串，避免 JSON float 精度损失；注销 phone_archive 在申请时刻定格（cancel_service.py:101），冷静期内换绑也能回溯原号。
