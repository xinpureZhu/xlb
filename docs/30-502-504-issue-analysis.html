502 / 504 问题分析

两类完全不同的故障：502 集中在效能平台的一个接口（后端服务在 prod 根本没有部署）；504 全部落在 external-split 跨集群切流边上（prod → prod-136，固定 10s 上游超时）。

upstream_service_time: 10008 / 10010 / 10024     duration: 10008 / 10010 / 10024

判读要点
  • upstream_service_time 与 duration 几乎相等且钉在 10s ⇒ 上游请求超时（固定超时被触发），不是随机慢、不是连接被拒。
  • bytes_sent=24 是 Envoy upstream request timeout 的固定短响应体（与本报关 502 的 67 字节形成对照）。
  • route_name=external-split ⇒ 命中的是老集群→新集群切流规则，与业务代码无关；同一域名下的本地流量正常。
  • 远端 IP 只有两个（172.16.120.145、172.16.185.105），两者都出现 504 ⇒ 不是「单个网关 Pod 生病」，而是这一段链路整体在超时。

06排除项与未覆盖边界 已排除 mesh/网络/业务代码；136 侧不可见

项结论
502 是否 mesh 返回否：response_flags="-" + upstream_host 已连到前端 Pod :4321 ⇒ 前端应用自身返回
502 是否本地服务过载否：前端 3 个 Pod 均在线、时延 12–19ms、无 5xx 之外的异常；只有一条上游地址失败
504 是否本地业务慢否：route_name=external-split ⇒ 请求被送去远端；upstream_service_time 全部≈10s，与本地后端耗时无关
504 是否单点故障否：两个远端内网网关 IP 都出现，且 13 个不同域名命中
136 侧为何超时本数据源不可达（136 有独立 VictoriaLogs/Trace）。需在 grafana-136 侧核对：远端网关是否收到该请求、远端应用耗时、远端是否有 10s 的 route/cluster 超时配置
顺带发现（同类「配置指向不存在的目标」） prod 的 efficiency-platform-web 自身日志持续打印 [OpenTelemetry Proxy] 转发追踪数据到: http://opentelemetry-collector--observability.test.xlbsoft.com/v1/traces 且 Collector 响应状态: 503 —— 生产前端把跟踪数据发往 .test. 域名并被 503 拒绝， 属于同类问题（目标错配 + 静默失败），建议一并纠正。

07修复建议 先把「目标是否存在」变成可校验的发布前置条件

P0 · 502：先决定「agent-square 是否该在 prod 有后端」，再消除裸 502
  • 若功能应在生产可用 ⇒ 把 agent-square 部署到 prod（当前 prod/prod-gray 均为 missing，只有 dev/test/staging 有）。
  • 若暂不上线 ⇒ 前端关掉/降级该调用（平台配置开关），或让代理在目标不可达时返回 503 + 业务可读文案，而不是 502 裸响应。
  • 该接口当前≈10 次/分钟稳定报错、用户可见，修复成本低、收益直观。
P0 · 504：给跨集群边路明确「超时预算 + 降级」
  • 10s 固定超时说明远端不响应直到超时。需要在 136 侧确认是「服务慢」还是「请求根本没到/被静默黑洞」；前者调优远端，后者排查远端网关的路由与安全组。
  • 跨集群路由应显式配置更短的单次超时 + 有限重试 + 失败回落本地（老集群权重兜底），避免用户端等待 10s 才拿到 504。
  • 把「远端权重」与「远端健康/时延」绑定：远端不可用时自动回落到本地，而不是硬等超时。
P1 · 可观测性与告警
  • 按 route_name + upstream_cluster 维度增加 504/502 比率告警：现在这两类问题都没有触发告警（同期该命名空间只有 HpaMaxedOut）。
  • 把「upstream_service_time ≈ 固定值」作为一种超时指纹纳入巡检：固定 10s/5s 直接指向超时配置而非业务慢。
  • 502/504 的 bytes_sent 可作为快速指纹：24 字节 = Envoy 上游超时体；67 字节 = 本次前端代理的自定义错误体。
P1 · 发布前置校验（覆盖本次两类问题）
  • 服务注册/路由发布时校验目标 workload 是否存在于目标环境（agent-square 这类「配置指向未部署服务」可被一次校验拦住）。
  • 跨集群切流放量前校验远端可用性（与 doc 28 的建议同一条）。

08排查口径备忘 别被查询语法和聚合口径误导

LogsQL 语法坑
  • response_code :> 500（Grafana 里的写法）在本环境返回 0 行 —— response_code 是字符串字段，数值比较不生效。请用 response_code:~"50[0-9]" 或显式 response_code:"502"。
  • 「5xx 的行数 ≠ 失败请求数」：同一请求会在 waypoint Pod 与 ingressgateway Pod 各记一条，统计数量时需除以 2（doc 29 的 236 行 = 118 个请求即由此而来）。
  • 跨集群远端流量的流标签是 namespace="istio-system" + svc="<upstream cluster 名>"，不是目的服务所在命名空间；按 {namespace="<业务 ns>"} 查会漏。
  • 字段位置：authority/path/response_code/upstream_cluster 等可直接过滤；route_name/upstream_host/bytes_sent 等在 _msg 内，需 unpack_json from _msg fields (...)。
