整体判断变化 这已不是「adapter + core 可用、其余四模块骨架」的项目。履约、逆向、结算、检索四域全部有实现，并各自拆出独立消费者模块；消息侧新增事务消息与死信队列。

03oms-core 订单核心 142 文件 · 已改用事务消息

  • 订单聚合与 COLA 状态机承载 PAID → CONFIRMED → FINISHED 主链路与各态到 CANCELED 的迁移，主链路语义未变。
  • 三个消费者拆分：orderpaid（已支付建单）、ordercancel（取消）、orderprint（73 文件，订单打印——新增的完整子域，含死信队列）。
  • MQ 生产者已升级为事务消息：OrderMQProducer 调用 xlbRocketMqClient.sendTransactionMessage(...)（:444），配合 TX_TOPIC。这实质性缓解了旧版指出的「发布先于提交、无 outbox」问题——半事务消息 + 回查可保证本地事务与消息最终一致。
  • Topic 常量：OMS_ORDER_TOPIC、OMS_ORDER_STATUS_CHANGE_TOPIC、OMS_ORDER_PRINT_TOPIC、DLQ_OMS_ORDER_PRINT_TOPIC、ADAPTER_TOPIC、TX_TOPIC。
可靠性改进 出现死信队列（DLQ_OMS_ORDER_PRINT_TOPIC）与 OrderPrintDeadLetterConsumerBootstrap（含单测）。旧版「重试耗尽后仅打日志、消息丢失无法追溯」在打印链路上已解决。

04oms-adapter 渠道接入 208 文件 · 最大模块 · 但仍无验签

  • 已成为全项目最大模块（208 文件），另有独立的 oms-adapter-callback-consumer 与 oms-thirdparty-adapter（28 文件）。
  • ChannelCallbackMessageGateway 已存在于 domain 层 gateway 包——旧版「接口缺失致不可构建」不成立。
  • 状态映射改为枚举驱动：ChannelOrderStatusMapping 枚举 + MeituanOrderPaidAssembler 使用 + 单测覆盖。旧版「建表却不读」已通过换实现方式解决——但 DB 表可能已成冗余，值得确认后清理。
Critical 仍在：回调无签名校验 渠道回调仍只做幂等与落库，不验证来源真实性 → 外部可伪造回调驱动下单、完成、取消。

建议：按美团开放平台规范实现 sig 校验（app_secret + 参数规范化 + 摘要比对），并加时间戳窗口与来源 IP 限制。

07风险清单（分级） Critical 由 4 降至 1~2

Critical

  1. 渠道回调无签名校验——唯一确定仍存在的 Critical。
  2. 明文凭据：旧版曾发现生产库与三方密钥以明文或 ${VAR:真实值} 形式入库。本次未逐文件复核，按未修复对待并优先审计。

待复核（旧版 High，本次未确认状态）

  • 幂等实现是否仍将 Redis 异常吞成「冲突」（fail-closed）。
  • finishOrder 是否仍在 DB 事务内调用库存服务。
  • InventoryService/PushService 是否仍为 stub（本次未见 TODO 命中，可能已实现）。
  • 幂等短路路径是否仍不重发事件。
  • BusinessCode 是否仍有 15+ 组重复 code。
  • 雪花 ID 的 32 IDs/秒瓶颈与 UUID 哈希分片是否仍在。
  • GraalVM 原生镜像是否已补齐 profile 与 reachability 元数据。
本篇核验范围说明 本次重写在有限预算内完成了结构性事实的全面复核（模块、分层、状态机、消息、控制器、AI 状态、验签状态），但未逐文件复核全部旧版 High/Medium 条目。上表已明确区分「已确认」与「待复核」。如需完整的 prod 风险清单，建议对 oms-core 与 oms-adapter 两个大模块做一轮专项审计。

建议优先动作

  1. 补齐渠道回调签名校验 + 时间戳窗口 + 来源限制。
  2. 审计并轮换 prod 配置中的凭据，统一走外部 Secret 管理。
