A业务上：以「单据 + 任务 + 库存」为主线

入库、出库、库存、基础资料、策略、自动化、预约、逆向、计费报表九大能力域，全部围绕仓储作业单据与作业任务展开。核心单据链是 入库申请 → 收货 → 质检 → 上架 与 出库申请 → 波次 → 拣货 → 分播/播种 → 复核 → 发运。

B技术上：两代实现并行，共享一个库

wms 单体仍是主力：Spring Boot 2.7 + Java 8 + JPA/QueryDSL，动态多数据源按公司路由。新服务 wms-basic / wms-outbound / wms-inventory / wms-bounding / xlb-wms / wms-inbound 用 Java 21 + Spring Boot 3 + MyBatis-Plus，但全部指向同一个 new_wms 库。

一句话判断 WMS 当前不是「微服务架构」，而是单体为核心、按子域逐步外剥的绞杀者架构。新服务已经承担基础资料、出库、库存查询、库存调整等读写，但数据所有权、事务边界和多租户路由尚未随服务边界一起切开，这是理解 WMS 一切技术取舍的前提。

CMDB 服务树把 WMS 归在供应链与履约 / WMS仓储管理，下挂 wms-web、wms、wms-outbound、wms-basic、wms-bounding、wms-export、wms-inbound、wms-inventory、wmshandle、xlb-wms 十个应用；wcs、sc-wcs、sc-appointment 作为仓储自动化与预约能力独立部署在 wms 命名空间。

04业务架构：作业域与能力地图 九大能力域，核心是「单据驱动任务、任务驱动库存」

01入库域

入库申请、预约/月台、收货、质检、上架、卸货、退货入库、越库。强调「到货前预约、到货后收货、质检后上架」。

02出库域

出库申请、出库单、波次、拣货、分播、播种、复核、发运、装车、配送交接。策略与任务编排最密集。

03库存域

库存主档、批次/效期、锁定、流水、快照；盘点、调整、移库、移储、货主转移、冻结、报损。

04基础资料域

仓库、库区、库位、容器、托盘、月台、车辆、员工、货主、客户、商品、批次、参数、告警、字典。

05策略域

上架、拣货、分播、播种、波次、补货、AGV 点位、效期控制、自动关单、扫码规则。

06自动化域

AGV/机器人任务、提升机、电子标签、格口复核、工作台、码货员、月台格口、库位坐标。

07预约域

预约任务、预约单、时段产能、签到、叫号、卸货、简写号、限制规则、开关配置。

08逆向域

退货入库、退货复核、出库冲销、理赔/认领、报损、异常订单监控。

09计费与报表

仓储费用、配送费用、经营报表、人效、库存分析、出入库差异、效期监控、BI。

12结论与建议 下一步不是「再拆几个服务」，而是把数据所有权、租户路由和一致性补上

  1. 先定数据所有权，再谈服务拆分。 对 new_wms 的核心表做「单写者」清单：单据、任务、库存、基础资料分别由哪个服务负责写，其他服务只能读或走 API。没有这张表，拆得越多，跨服务写冲突越多。
  2. 把租户路由补进新服务。 单体的 company_id → dbname 是生产事实，新服务不能假设只有一个库。要么在数据访问层实现同样的路由，要么明确「一个租户一套部署」，并在网关注册时标注租户范围。
  3. 跨服务一致性用 outbox/事件，而不是只靠 Engine 任务。 Engine 任务适合编排，不适合作为唯一的一致性保障。关键链路（出库扣减、入库上架、库存调整）应有事件表、消费幂等和对账。
  4. 完成或撤下 wms-inbound。 当前它不是可运行的入库服务：没有 Controller，配置名和 Job 名都指向别的服务。要么补齐用例与部署清单，要么从 CMDB/流水线中标记为「未就绪」，避免误发布。
  5. 统一入口鉴权。 网关做身份，服务做授权；逐步淘汰 Redis access_token 与静态 client token。开放接口的白名单必须纳入 GitOps 审计。
  6. 把架构规则变成测试。 至少覆盖：domain 不依赖 external、PO 不出 persistence、禁止 @Transactional、跨子域不互调。规则写在文档里会被绕过，写在 ArchUnit 里才会失败。
  7. 修正文档漂移。 先改 wms-inventory/CLAUDE.md 的“MDM”描述，以及 wms-outbound 的事务规则与 WaveStrategyAppCmdService 的冲突；否则后续 AI/新人会持续按错误前提改代码。
  8. 保留两代并行的现实。 短期不要追求「单体全部拆完」。更现实的路径是：单体继续承载复杂作业编排，新服务承接可独立闭环的基础资料、库存查询、库存调整、容器/越库；每抽一个域，先切数据所有权与租户路由。
值得肯定的部分 WMS 的新服务并不是“为了微服务而微服务”：wms-outbound 有明确的分层规则、client SDK、事务模板和防腐层；sc-appointment 把预约做成独立限界上下文并写清了贫血模型的选择；sc-wcs 把设备调度、格口、电子标签从旧 wcs 中拆出来。这些边界是对的，问题在于数据面还没有同步切开。
