最严重的发现：生产 JWT 密钥是可猜字符串 gitops 中 JWT_SECRET 的 prod 值是完整的字母表序列（0123456789ABC...xyz）。任何人可为任意 C 端会员签发合法 token，绕过 mp-bff / bff_retail 的全部 AuthGuard；配合下文的积分下单缺口，可任意冒名下单、消费他人积分/储值/券。
鉴权装配的系统性缺陷
  • xlb_retail_bff_pos（prod 400-450 副本）与 auth-server 的 AuthGuard return true 无条件放行——两者都实现了 getUser() 却从未调用，@NoNeedLogin() 装饰器全是死代码。
  • cms-server 用 jwt.decode() 不验签，且 iAuth 权限校验被注释掉。
  • cms-server-c 形态（prod 80-150 副本 + 公网可达）完全没有注册全局 Guard——Guard 只在 APP === 'cms' 时注册，而同一镜像的全部 admin 写接口在 C 端形态下零鉴权暴露。
  • xlb-mp-bff 的 ForwardMiddleware 代理链路同样只 decode 不验签，却把解析出的 memberId 写进下游转发头。
  • auth-server 还暴露一个转储全部缓存 token 的接口——内网任意调用方可拉取微信/支付宝/快手/抖音/乐檬全平台的 access_token 与 refresh_token 明文。

03遗留 BFF 双活风险 安全补丁只覆盖一半生产流量

遗留仓仍在生产双活 gitops 显示 mp-bff（镜像 bff-retail）prod 为 true、minReplicas 20 / max 200，且其 prod 制品 SHA 与 xlb_bff_retail 本地 HEAD 完全一致。两套代码同时在生产接同类 C 端流量。

1安全补丁只打在新仓

同一批 /order/point/* 接口，遗留仓 4 个漏洞全未修。攻击者只需把请求打到遗留域名而非新域名，即可用他人积分下单、跨公司下单。

2灰度语义不兼容

旧仓读 whitelist:point，新仓读 canary_whitelist:point 且需要总开关；同一用户在两条链路上会命中不同的会员资产数据源（旧 ES vs V2 ES）→ 读写视图分裂。CLS 键名也不同，下游按旧键判断的逻辑在新仓恒为 undefined。

3共享 Redis 与队列

两仓共用同一 Redis 与同一 Bull 队列名，旧仓的 Processor 可能消费新仓投递的任务（反之亦然），而两边卡类型枚举与服务实现已分叉。

4新仓的正向改进

Token 调试日志改为仅非 prod 输出（旧仓无条件 console.log 解码后的 token）；新增 marketing-activity-player 模块与 V2 会员资产 ES；删除了乐檬相关代码。

但也有退化：证书配置从「文件路径」改为内联私钥内容 → 明文 PEM 进 gitops YAML；灰度匹配从 SISMEMBER（O(1)）退化为 SMEMBERS 全集拉取到内存（O(N) + 每请求全量传输），且匹配手机号末 1/2/3 位——白名单里放一个 "8" 即命中全量 10% 用户。

04auth-server Token 代理 无防击穿 · 支付宝 key 读写不一致

平台TTL 策略问题
乐檬 LMaccess 用 expires_in；refresh 无 TTL（永久）读取路径不查 Redis直接刷新；30 分钟定时刷新在每个 pod 独立执行（无分布式锁），N 副本 = N 次刷新，refresh_token 轮换型接口下可能互相踩失效
微信 MP / 公众号expires_in - 60缓存过期瞬间 N pod × M 并发全部打微信，且 getStableAccessToken 会使旧 token 失效 → 短暂全站 token 抖动

快手 / 抖音access −1h / refresh −5 天常量名与值错配（ALIPAY_REFRESH_TOKEN 的值是 CACHE_WX_ALIPAY_TOKEN）

05cms-server 权限模型 三重失效 · 门店隔离是死代码

权限元组结构为 {user_id, authority:{app_type:'MEM', path:'小程序装修'|'空白码管理', action:'查询|新增|编辑|删除'}}，经 iAuth 的 internal.authority.check 校验。但实际有三重失效：

  1. Guard 层的批量校验被整段注释掉。
  2. JWT 不验签（jwt.decode）——只要带任意 Bearer <base64>，name 与 company_id 由攻击者自定义。
  3. 权限校验下沉到 Service 且条件可绕：调用形如 if (headers) { checkAuthority({user_id: headers['user-id'], ...}) }——user_id 直接取自未认证的请求头，伪造成任意管理员 id 即通过；headers 未传则整段跳过。空白码批次创建/更新的权限校验被整块注释。
租户与门店隔离未实现 UserInterface 声明了 storeId/userStoresQuery/admin/userType，但 userStoresQuery 全仓仅定义处一处、零引用——门店维度数据隔离完全是死代码；storeId/admin/userType 同样从未被任何服务读取。company_id 仅在空白码导出时用于过滤，且值来自未验签的 JWT → 篡改即可导出其他公司的数据。权限粒度也只有 app_type='MEM' + 两个 path，不含 company/store 维度。

空白码与企微活码业务流：Admin 面 24 个 POST（批次 CRUD、导出、码管理、场景、排期、版本）；App 面全部 @NoNeedLogin()（含 batch/bind）→ 未鉴权即可批量绑定/查询空白码；企微活码 7 个 admin 写接口完全没有任何权限校验调用。唯一定时任务每分钟扫排期且无分布式锁，多副本重复执行。

图 2 · POS 结算的身份信任缺口

  • body.customer_id 完全被信任——传了就跳过整个付款码→会员解析链路，可把交易/积分/权益挂到任意会员头上。（company_id 走服务端配置，这点比 mp-bff 好。）
  • 会员解析异常被吞且日志级别是 info，失败后继续结算。
  • member:canary 灰度逻辑缺陷：Redis string 类型用 String.includes() 做子串匹配 → 白名单含 "1234567" 时 member_id=234 也命中；member_id 取自请求头，任何 POS 都能自行进入/规避灰度；每请求一次 Redis GET（400 副本 × QPS 全打同一 key）；通过改写 request.body.selfDeveloped 切链路（DTO 里无该字段，污染透传）。
  • 组合接口「核销 + 下单 + 支付」串行且无幂等/补偿 → 核销成功但支付失败即券损失。
  • 全局热数据开关可被无鉴权写入，配合 Guard 恒放行 → 任何人可全局切换数据源。
  • 以完整 access_token 作 Redis key 后缀 → token 泄漏面扩大到 Redis。
  • bigNumberStrings: false + bigint 主键 → 大整数转 JS number，>2^53 精度丢失。
  • 生产代码里无条件注册测试模块。

正向：19 处数据访问全部使用 TypeORM createQueryBuilder，未见字符串拼接 SQL（无注入）；DB 账号为只读；未开 synchronize。

07mall-mcp 骨架 确认非功能性 · git 无任何提交

确认为纯空壳：git 无任何提交；全仓无 MCP SDK、无 transport、无 HTTP server；「server」只导出一个 getHealthStatus()；API client 全部返回回显对象与空数组，无一行网络调用。有 node --test 单测但只测内存 mock。

8 个规划的 tool 契约：search_products、get_product_detail、get_cart、add_cart_item、update_cart_item_quantity、remove_cart_item、create_order_from_cart（需显式 confirmed:true）、get_order_status。共享上下文 MallContext{storeId,userId,sessionId,requestId,locale,currency}，统一错误模型含 retryable 标志。spec.md 中已写入真实上游 Swagger 地址与 curl 示例。
