分析基准：仓库 goods_consumer（服务 erp-stock-sync），分支 prod， 提交 dac1aa6，提交日期 2026-07-28，与远端 origin/prod 差距 0 / 0（一致）。 工作副本位于 repos/goods_consumer，为只读克隆。

本文记录的是 prod 现行口径。2026-12-09 迭代分支上的改动与 prod 的差异单独列在 §11，不与本文口径混用。

一句话结论：所有商品（标准品与组合品）共用同一条主干——把 item 的可用量按库房/批次求和成「成分总量」， 按配比相除取最小值得到「可售套数」，再对每个启用渠道乘安全比例、减锁定库存，分别写 Redis 与 Mongo。 标准品只是「只有一个成分、配比为 1」的特例；真正的分支判断都在渠道层（门店库存类型、渠道库存类型、渠道白名单）。

数量一律用 f64 承载（落 Redis 时格式化成 4 位小数），套数落库前 floor 成整数。 组合品取 min、向下取整、负可用量合法，是理解线上数字的三条底线。

03商品形态与库存类型 公式只有一条，分支全在"要不要写这个渠道"

ERP 同步链路里没有"商品类型（虚拟/实物）"的概念，只有库存类型。判断依据分散在三处：

判断对象取值来源判定影响
门店库存类型{store}:C 的 TT == "0" → 实时；其余（含缺失）→ 虚拟决定 viola_tricolor 是否被跳过
普通渠道库存类型渠道 hash 的 TT == "0" → 实时；其余 → 虚拟决定售罄迁移是否参与
积分渠道库存类型INVENTORY:{point}:{sku} 的 STOCK_TYPE"1" → 实时；其余 → 虚拟虚拟时整条积分渠道不写
标准品 / 组合品{SI}:{sku}:I 的成员数1 行且配比 1 → 等价标准品；多行 → 组合品不改公式，只改 min 的项数

于是"各种商品"的差异收敛成一句话：组合品是多成分取 min，标准品是单成分取自身；虚拟/实时只决定某个渠道写不写、售罄发不发。

04第一层：item 可用量 每个库房（或库房+批次）一行，带时间守卫

ERP 的 stock_detail 变更逐行映射成 Redis hash 的一个字段：

项公式 / 规则
Redis key{store_id}:{item_id}
fieldbatch_number 非空 → {storehouse_id}:{batch_number}；否则 {storehouse_id}

flowchart TB

  B --> C{"new_time 小于 old_time"}
  C -->|是| X["EXPIRED 跳过重算"]

图 2 · 计算流水线：从一条 ERP 行到渠道可用量与售罄事件

成分总量（对某个门店与某个 item）：

Q(item) = Σ  parse_qty(value)          value 遍历 {store}:{item} 的所有字段
parse_qty(v) = v.split(':')[0].parse::<f64>().unwrap_or(0.0)

即：同一 item 的所有库房与批次行一律相加；字段值取冒号前的数量部分。item hash 不存在时 Q = 0。

可售套数（对某个门店与某个 sku）：

units = floor( min over 每个成员 e of  Q(item_e) / ratio_e )

ratio 缺失 / 非数字 → 1.0            ratio 为 0 → Q/0 = +inf（在 min 中等于被忽略）
任一项为 NaN → 视为最大（不参与 min）  全部为 NaN → 结果 0.0

同一成分出现多行时，prod 用「最大配比」而不是「配比相加」。例如成分集合是 A:1、A:2、B:1，A 总量 100、B 总量 100：

  • prod：min(100/1, 100/2, 100/1) = 50 套；
  • 若把同一 item 的配比相加（A:3）：min(100/3, 100/1) = 33 套。

也就是 prod 口径更乐观。这是复现线上数字时必须照抄的细节，2026-12-09 迭代分支已按此对齐。

标准品就是这个公式的特例：{SI}:{sku}:I 只有一行 "item:1"，于是 units = floor(Q(item))。

06第三层：渠道可用量 乘 P → 减 Redis LOCKED → 分别落 Redis 与 Mongo

对每个 sku，遍历该门店所有启用渠道（{store}:EC 中值不为 "false" 的键）：

ch_qty   = (units * P) / 100                       // i64 整数除法，向零截断
ch_avail = ch_qty - LOCKED_redis                   // Redis 侧判售罄与写 AVAILABLE 用它

Redis:  HSET  {store}:{channel}:{sku}  AVAILABLE  ch_avail
        HSET  {store}:{point}:{sku}    AVAILABLE  ch_avail      // 积分渠道写这把键
Mongo:  overwrite_channels.{ch}.quantity           = ch_qty
        overwrite_channels.{ch}.available_quantity = ch_qty - ifNull(locked_quantity_mongo, 0)
        quantity = available_quantity              = units

两个 locked 来源不同：Redis 的 AVAILABLE 用 Redis 里的 LOCKED； Mongo 的 available_quantity 用 Mongo 文档自己的 locked_quantity（由 Mongo 聚合表达式现算）。 两者不同步时同一 sku 会在 Redis 与 Mongo 里显示不同可用量——这是设计如此，不是 bug。

渠道层细节规则
P 取值渠道 hash 的 P；缺失 → 门店 {store}:C 的 P；再缺失 → 100。积分渠道的 P 取自 INVENTORY:{point}:{sku}
LOCKED 取值普通渠道取该渠道 hash 的 LOCKED；积分渠道取 {store}:{point}:{sku} 的 LOCKED（缺失 → 0）
跳过 1：门店虚拟 + viola_tricolor整条渠道不写
跳过 2：sku 的积分库存类型为虚拟积分渠道不写（其它渠道不受影响）
跳过 3：未知渠道名且不安全名字为空 / 以 $ 开头 / 含 . → 跳过并 warn（防止污染 Mongo dot-path）。已知渠道名不受限
写入粒度该门店全部启用渠道覆盖式写入，不是增量：一个 sku 一次重算会写它的每个渠道
Mongo upsertfilter {sku_id, store_id}，upsert=true；created_at/created_by 用 $ifNull 只在首次插入时生效

即使该 sku 没有任何渠道可写（全被跳过或门店未配置渠道），prod 仍会把顶层 quantity / available_quantity / updated_at 写进 Mongo。 所以"门店渠道全关"的商品在 Mongo 里依然是被维护的。

07售罄迁移 只认 official 且实时库存，基于"写前旧值"判方向

渠道层算完之后，只有满足 channel == official 且该渠道库存类型为实时时才判售罄：

old = 写入前 Redis 里的 AVAILABLE（读渠道 hash 得到；积分渠道不参与）
new = ch_avail

old > 0  且 new <= 0  →  SoldOut
old <= 0 且 new >  0  →  InStock
其余                   →  不发消息

命中迁移后：从 goods.product 读该 sku 的 overwrite_channels.official.catalogs[]， 每个 catalog 发一条 UPDATE 到 GOODS__KAFKA__TOPIC__OFFICIAL_PRODUCT_SYNC， key = {sku_id}-{store_id}。没有 catalogs（或没有 official 节点）就什么也不发。

旧值是"写入前读到的 Redis 值"，与写入不是原子的：同一 sku 被并发重算时可能漏发或多发一次迁移。 这是 prod 的已知薄弱点，新版本已改为用写入脚本返回的旧值判定。

08精度、取整与负数 f64 求和 · floor 向 -∞ · 整数除法向零

位置类型 / 规则例子
ERP 原始数量字符串 4 位小数，按 f64 解析"-6.0000" → -6.0
item 落 Redisformat!("{:.4}")-6.0 → "-6.0000"
成分求和f64 累加（二进制浮点，非十进制精确）多个 4 位小数量相加可能落在整数下方一点点
套数取整f64::floor()，向 -∞2.9 → 2；-2.1 → -3
安全比例i64 乘法后整数除法，向 零 截断(-3 * 50) / 100 = -1（不是 -2）
P 的语义百分数：100 = 不打折；大于 100 会放大库存units=3、P=90 → 2
LOCKEDi64，直接相减2 - 5 → -3（可负）

这三条取整规则方向不同（floor 向 -∞、整数除法向零、f64 累加误差），复现线上数字时最容易踩坑的就是 "边界值差 1"——它来自 f64 累加/除法，而不是业务规则。

09三个算例 标准品 / 组合品 / 重复成分行

A标准品 · 实时门店

门店 S：T=0、P=100；item I 库房 W 无批次。

ERP 行：basic=-6.0000、lock=0.0000 → 字段 W = "-6.0000:ts"。

{SI}:sku:I = ["I:1"] → units = floor(-6/1) = -6。

official：ch_qty = (-6*100)/100 = -6，LOCKED=2 → AVAILABLE = -8。

Mongo：quantity = available_quantity = -6；渠道 quantity=-6、 available_quantity = -6 - MongoDoc.locked_quantity。

B组合品 · 虚拟门店

门店 T=1（虚拟）、P=90；sku 成分 A:2、B:1。

Q(A)=10、Q(B)=3 → units = min(10/2, 3/1) = 3。

ch_qty = (3*90)/100 = 2（整数截断）；LOCKED=0 → AVAILABLE = 2。

渠道分支：official（渠道 T=0）→ 写；viola_tricolor → 门店虚拟 → 跳过； 积分渠道（STOCK_TYPE≠1）→ 虚拟 → 跳过。

C重复成分行

成分集合 A:1、A:2、B:1；Q(A)=100、Q(B)=100。

prod：min(100/1, 100/2, 100/1) = 50 套。

若改成"同一 item 配比相加"：min(100/3, 100/1) = 33 套。

差 17 套。复现线上数字必须按前者。

2同一成分多行、配比不同按 max(ratio) 计，偏乐观（可能超卖）。需确认线上是否存在这种数据
3f64 累加/除法落在整数下方套数比"精确计算"少 1（如 0.3/0.1 → 2.999… → 2）。只在边界值可见；迭代分支 2026-11-27 已回退到同一行为
