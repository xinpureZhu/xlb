05根因：目标实例缺少该回调入口 prod 实例 8 天窗口内 0 次成功；gray 实例 100% 成功

核查项结果说明
prod oms-adapter 是否成功处理过该路径0 次（10-08 → 10-16）检索 "/adapter/callback/jdmiaosong" + "status=200" 无命中 ⇒ 该实例从未提供这套入口
oms-adapter-gray 是否成功全部成功返回 {"msg":"success","data":"","code":"0"}
是否由 prod 应用发版引入否事故期间 prod 实例一直是同一 RS 68cd584d56（起始时间 ≈ 2026-08-19），期间无重建
是否所有子类型都坏是（15/15）按路径聚合全部为 500，定向到「整套 jdmiaosong/djsw 前缀缺失」而非个别接口
回调 Controller 组织方式（代码）@RequestMapping("/callback/meituan") 等oms-plateform/oms-adapter 现有 美团闪购 / 淘宝闪购 / 美团 MOP 控制器；本机 prod 分支（2026-08-06）中检索不到 jd_miaosong / djsw（该克隆可能滞后，仅作旁证）
两个独立缺陷叠加
  1. 路由目标错误：回调路由（运行时配置，非 gitops）指向了没有该入口的 prod 实例。既有部分路由已指向 -gray， 说明这是一次「迁移/灰度」过程中的不一致，而不是灰度开关整体误开。
  2. 错误语义被吞掉：NoResourceFoundException（配置类错误，语义接近 404）被全局异常处理器统一包装为 500 「系统繁忙，请稍后重试」。结果是：京东侧看到的是 500（会按 5xx 策略重试/告警）， 排障人看到的是「系统繁忙」这种无信息量的文案，而真正的信息（路径不存在）只在 ERROR 栈里。

06影响面与恢复 京东秒送订单全生命周期回调：建单/锁单/拣货完成/出库/配送/取消/售后

  • 业务对象：channel_id=jd_miaosong、x-jos-vender-id=174994658、x-company-id=66666， 涉及门店（storeId）24591798、24522427 等；消息类型含 orderCreated、orderAdjust、 o2o_afs_state_change、waitProcessCancelRequest。
  • 失败语义：京东推送被网关 100% 拒绝（500），该批订单的状态变更没有进入 OMS，需要京东重推或人工补单。
  • 失败规模：118 次请求 / 15 类回调 / 2 个时间窗；单笔订单生命周期中若 newOrder、lockOrder 同时失败， 会直接影响接单与履约时点。
  • 恢复路径：路由改投 oms-adapter-gray 后回调恢复 200；对失败窗口内的历史消息是否全部补投， 本次仅抽检了 1 个 delivery_id（1c7cf564-…），在网关日志中未再出现，说明网关层没有自动重投记录 —— 该结论不足以证明业务已补齐，需要与京东侧/业务侧核对未落单订单（见 §8）。
告警缺失（本次最值得优先补的一环） 故障持续 5 小时 20 分钟、118 次失败，期间该命名空间触发的告警只有 HpaMaxedOut（warning，与本次无关）。 也就是说：同样的事故再来一次，仍然依赖人工翻 Grafana 才能发现。

怀疑项核查结果
mesh / 网络response_flags="-"、upstream_host 已连通应用 :3000、24ms 完成 —— 无 UF/UH/URX/DC
网关进程健康同期其它通道（如 meituan_shangou_*）回调正常 200/ack；retail-thirdpart-gateway 未重启

08修复建议与遗留问题 先让语义正确、再让配置防错、最后让告警能看见

P0 · 消除过渡态：prod 实例补齐入口 + 路由回切
  • 当前所有 jd_miaosong 回调都依赖 oms-adapter-gray 这一灰度实例。 一旦 gray 缩容/重新发版/被清理，回调会立刻退回 500（因为 prod 实例仍没有入口）。
  • prod oms-adapter 已于 10-15 20:42 重建（新 RS 6bd978dbc4），需确认该版本是否已包含 /callback/jdmiaosong 入口；确认后把路由回切到 prod 实例并复验，再回收这条过渡配置。
P0 · 修正异常语义（低风险高收益）
  • 把 NoResourceFoundException（以及同类「无匹配 handler」异常）从 GlobalExceptionHandler 的 500 分支里摘出来，映射为 404 / 400，并保留原始 URI。
  • 理由：这类错误本质是调用方与提供方的路径契约不一致，用 500「系统繁忙」掩盖会同时误导两侧： 调用方按 5xx 重试（无意义重试），提供方按「系统故障」排查（其实没有故障）。
P1 · 配置防错：路由目标与实例能力必须绑定
  • 回调路由（channel_id + route_id + forward_url）由运行时配置写入， 没有任何「目标实例是否实现该路径」的校验。建议在 retail-thirdpart-gateway-admin 保存/发布路由时做一次 目标探测（对目标实例发一次探活或读取其路由清单），不一致就拒绝发布。
  • 发布/迁移类变更应支持试运行：先按 1 条路由灰度到新目标，观察真实流量成功率，再批量切换。
P1 · 告警与可观测性
  • 新增按「通道 + 路由」维度的回调失败告警（网关 callback delivery returned non-success status 日志计数， 或 dispatch_status != 200 比率），阈值取「>3 次/5 分钟」即可覆盖本次场景。
  • 接入侧观测建议：response_code 是字符串字段，response_code :> 500 在该 LogsQL 版本返回 0 行 （已实测），请改用 response_code:~"5[0-9][0-9]" 或显式枚举 —— 否则会出现「面板无数据 = 没有问题」的错觉。
本次排查的可复用要点
  1. 寻找 5xx 时先看 response_flags："-" + 有 upstream_host + 毫秒级 duration ⇒ 应用自己返回，别在 mesh 上耗时间。
  2. 网关类服务会把「下游状态码」原样透传并落一条带 forward_url 的日志 —— 这条日志直接给出下一跳是谁，是跨服务定位的最短路径。
  3. No static resource … 是 Spring Boot 3 的「没有匹配 handler」信号：对比 -gray 与 prod 实例的同一路径，能一次区分「能力没发布」与「路由指错」。
