1优惠券引擎（Decimal）

策略模式，7 步流水线：金额校验 → 商品范围过滤 → 门槛金额计算（可排除促销/会员/找零商品）→ 适用与可抵扣项过滤 → 使用次数限制（含循环倍数）→ 折扣计算 → 回写购物车。

分摊按 item_due/total_due 截断到 2 位，末项吸收舍入残差——这点做得对。券商品优先于其它券处理。

calculator/validator.rs:21-34,182-203,467-487,574-579

2促销引擎（f64）

Money(f64) + (v*100).round()/100——浮点金额，与优惠券引擎的 Decimal 不一致。5 种类型：单品折扣、特价、限时秒杀、第三件半价、跨品第三件半价。

选择逻辑：按优先级分组倒序遍历，组内取 promo_price × promo_quantity 最小者。

promotion/mod.rs:19-24,55-63 · simple_promotion_engine.rs:46-98
引擎层面的确定性缺陷
  • 同优先级组内的冲突判定失效：冲突只查 applied，而它在每组结束时才填充 → 同优先级的两个互斥促销都会生效。仓库自带测试就注册了两个 priority 90 且 set_conflict 的促销，该冲突从未触发。
  • 生产环境优先级与冲突机制完全惰性：两个入口都把所有促销注册为 priority 10 且从未调用 set_conflict → 引擎退化为纯粹的最小价选择器，PromotionRelation 四种关系与 can_combine() 全是死代码。
  • 两引擎选出不同赢家：simple 的比较器忽略 regular_quantity，graph 引擎却计入。
  • Money 券返回面额而非实际抵扣额 → 调用方多减。
  • calculator/mod.rs 是一条并行的死校验链，且与 validator.rs 逻辑相反（一个在 member_id.is_some() && !flag 时拒绝，另一个在 member_id.is_some() && flag 时拒绝）。该文件 717 行里约 560 行是内嵌 JSON 测试数据。

simple vs graph feature：simple（默认）无额外依赖故 WASM 兼容，是 coupon-web/coupon-assembly 唯一使用的引擎；graph 基于 petgraph 提供环检测与拓扑排序，功能更强但从未在生产启用。

03会员动态码 无密钥 · 校验形同虚设 · 不可作为鉴权因子

time_slice = unix_secs / 60
offset     = (time_slice × 7919) mod 1e8
encoded    = (card_code + offset) mod 1e8
输出        = format!("{:02}{:08}", time_slice % 100, encoded)
该方案不提供任何安全性
  1. 不存在密钥：7919 是硬编码常量（模块注释里就写着），time_slice 来自墙上时钟 → 任何人都能为任意卡号生成有效码，也能反解任意观测到的码。源码注释声称「可防止重放攻击」，该说法不成立。
  2. 时间标记从不校验：解析时直接切掉前两位，从不与 time_slice % 100 比对——前两位是装饰性的。
  3. 几乎任何 10 位数字串都能解析成功：唯一的完整性检查在前置条件下恒真（u64.to_string() 必然 ≤8 位 ASCII 数字）。无校验和、无 MAC。parse("0000000000") 会返回一个看似合理的卡号。因此 ±2 时间片的回退逻辑是不可达死代码。
  4. 重放窗口 3-5 分钟：码在整个 60s 片内稳定，解析又接受 −2..+2 片，且无 nonce、无一次性消费记录。
  5. 前导零丢失：返回未补零字符串，卡号 00123456 往返后变成 123456。测试用例恰好都用非零开头，故从未发现。
  6. 请求路径上有 panic：时钟回拨会命中 .expect("Time went backwards")。
结论：动态码只能作为展示层混淆。修复需要服务端对 (card_id, time_slice) 做 HMAC 截断进码内，并配重放缓存。

04路由决策中心 规则引擎可用 · 但配置加载会静默失败开放

规则模型：MatchField{phone,storeId,code,coupon} × MatchOperator{exact,suffix,missing,regex}，支持 AND/OR 嵌套，输出 {targetServiceKind: xlb|wc, targetEnvironment: prod|gray}，并可导出 DSL 给多端客户端。

三处严重缺陷
  • 配置加载静默失败开放：缺表错误会回退为空规则集（全部流量走默认路由）；父节点读取失败被 .ok() 吞掉 → 节点重挂到根，改变 AND/OR 语义；enabled 不可读时默认为 true；多个根节点时静默只保留第一个。
    route/config_loader.rs:202,214,222,313,341,349-353
  • 缓存刷新无投递保证：Redis pub/sub 是 at-most-once，无轮询兜底、无版本校验 → 正在重启或退避中的 pod 会永久提供陈旧路由。发布方还丢弃了订阅者计数；流正常结束会导致无退避的重连循环。

图 2 · 网关入站验签与出站代理的鉴权缺口

  • 签名规范化允许参数走私：k=v 用 & 拼接且不做转义 → 不同参数集可产生相同待签串。飞鹅还把空值参数排除在签名之外，攻击者可追加未签名但仍被转发的参数。
  • 回调无重放保护：无 nonce、无时间戳窗口、无内容派生的幂等键（delivery_id 是新生成的 UUID）→ 抓取到的已签名回调可重放成重复下游投递（重复订单/重复打印）。
  • 出口治理失败开放且泄漏配额：任何 Redis 错误即放行；配额在后续限流拒绝时已被消耗且无补偿回退；采用滚动窗口允许 2× 突发 → 可能导致合作方 API 封禁。

图 3 · ERP 库存同步管道的原子性缺口

  • 跨渠道重算非原子：Lua 的原子性只覆盖单字段 HSET；「读 item hash → 取 min → 写 AVAILABLE」整体是普通读改写。派发是轮询而非按 (store,item) 哈希分区，同一 SKU 的不同库位/批次字段必然落到不同 worker 上竞争 → 实时库存丢更新。
  • 跨分区排序被 offset 去重破坏：用 m.offset() 作序号且比较时不带分区，而 Kafka offset 只在分区内可比 → 同 key 落不同分区时排序无意义，旧记录可能胜出。Lua 的时间戳守卫部分补偿了这点，但时间戳解析失败会 unwrap_or(0) → 0 < old_time 恒真 → 畸形时间戳会静默把更新丢弃为 EXPIRED。
  • RocketMQ 监听器内有无超时的阻塞 HTTP 调用：block_in_place + block_on 且 reqwest::Client::new() 未设超时 → 上游挂起会占死运行时 worker；JSON 解析错误返回 FAILURE → 毒消息无限重试。
  • 所有 Kafka 客户端关闭了 TLS 校验，RocketMQ 亦关闭 TLS → SASL_PLAIN 凭据走未验证通道。
