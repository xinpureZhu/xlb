01结论与判据 用例归仓可行且更对，但必须配齐「版本绑定 + 内容寻址 + 元数据契约」三件前提

结论：冒烟/压测用例放进各自服务仓的 perf/，是这套体系的正确归属——用例与接口契约同仓、同 PR 评审、由服务负责人维护，覆盖率天然随服务仓走。 但「k6 只负责执行」要拆开看：平台承担的不是「跑用例」，而是「确保跑的是那个版本的那份用例，并且结果可信」。缺任一前提，方案就退化成「脚本在仓里、集群跑默认分支最新版」的不可信门禁。
3必须补齐的前提：版本绑定 / 内容寻址 / 元数据契约
1执行面已存在：k6-operator + ConfigMap 形状（仅 test 集群）
0平台接线现状：无 job_type=smoke、无 smoke-gate 节点

三条判据：

  1. 归属下沉是对的：用例断言的是业务语义（业务码、状态机、幂等、副作用可查），这些知识只在服务仓里；放集中仓会让 300 个服务的用例全部经由一次跨仓评审，演进速度跟不上接口变更。
  2. 执行面必须统一：集群里已有 k6-operator（grafana-k6/k6-operator.jsonnet，守卫「仅 test 集群部署，用于业务压测」），脚本语言统一为 k6 原生 TS/JS——Java / Go / Rust / Node / Python 服务共用同一运行时。
  3. 分散的代价要用治理补：「覆盖率看不见、共享库漂移、脚本与部署版本脱钩」是三个必然退化点，必须在方案里一次性设计掉（见 §07）。

02分工边界与三条编排路线 服务仓=内容 · gitops=开关 · 集群=执行 · 「编排与判定」可由平台 / Argo 节点 / Rollout 任一层承担

原方案把「编排与判定」整体压在平台的 job_type=smoke 上（下称路线 P）。要去掉这条依赖，先把平台在这条链路里提供的东西拆成 4 层，逐层问「谁必须做 · 能不能不依赖平台 · 去掉后谁接手」。结论：前 3 层都能挪走；第 4 层里「让发布单就绪判定引用冒烟记录」挪不走。

1节点实现天生在集群侧

环境子流程 YAML 只声明 DAG 与参数，节点实现是 templateRef 指向集群里的 WorkflowTemplate（cicd-node / job-executor / quality-gate-polling）→ 新增一个自包含节点＝新增一个模板文件，形状可直接抄 quality-gate-polling.yaml。

2接入是配置动作

平台已提供模板全生命周期 API：/workflow/templates 的 import-yaml / create / publish / rollback，/workflow/flows 的 draft/publish，加 /workflow/node-capabilities/refresh——导入模板、挂节点都不改 Go 代码（router/workflow/template.go）。

3能力抽取自动完成

平台把 deploy/argo-workflows 下的 YAML 作为 seed 导入并抽取 NodeCapability（pkg/workflow/service.go:41、pkg/workflow/flow_capability.go）；节点只要按 inputs.parameters 声明参数，就自动进能力清单。

4上下文可自给

不需要平台把 sha 传下来：Rollout 镜像 tag 内含 40 位 commit，注解内含分支 ID 与父流程 ID（efficiency/codeBranchId、efficiency/orchestrationWorkflowId）。

03TestRun 执行流程（细化） 8 个阶段 · 判红只看三件事 · 与选哪条编排路线无关

这一段是执行面本身：无论编排由平台、Argo 自包含节点还是 Rollout AnalysisRun 承担，「怎么拉起来 → 怎么等 → 怎么判红 → 证据留在哪」都是同一套。阶段名与 §08 接线清单里的 resolve / run / judge / record 一一对应。

阶段输入动作产出失败处置
S0 解析上下文workflow 参数：service_name / environment / 目标命名空间读 live Rollout：容器镜像 tag、efficiency/codeBranchId、efficiency/orchestrationWorkflowId；反解 40 位 commit sha 与 stable / canary Service 地址{sha40, imageRef, branchId, orchWfId, targetURL}Rollout 不存在或 tag 内无 40 位 sha → 判红 context_missing 且不重试（上游部署已异常）

S2 契约校验perf/k6.config.json解析 templateVersion、本环境命中的 suites、entry 是否存在、tags / thresholds 是否齐全；每个套件＝一次独立 TestRun（指标不混算）本环境套件清单（为空＝「未接入」，按 gitops 开关决定放行或判红）元数据缺失 / entry 不存在 / 阈值为空 → 判红 contract_invalid，不重试
S3 内容寻址打包脚本目录 + sha生成 ConfigMap k6-scripts-<svc>-<sha8>，key 用仓内相对路径，打 labels{sha,service,suite}名字即寻址的 ConfigMap（sha 变了就是新对象）同名已存在且内容一致 → 复用（幂等）；同名内容不同 → 判红（说明有人手工覆盖）
S4 拉起 TestRun套件元数据 + ConfigMap + 凭据 Secret创建 TestRun：parallelism: 1、script.configMap、runner.image、envFrom: secretRef、arguments（字符串）TestRun k6-smoke-<svc>-<sha8>-<env>CR 创建失败（CRD / RBAC 缺失）→ 判红并直接打印前置检查项
S5 等待终态TestRun 名轮询 .status.stage 直到 finished / error；节点超时 > TestRun 超时，双层兜底终态 + 实际耗时节点超时 → 判红 timeout；先删 TestRun 释放 runner 资源，再采证据
S6 判定终态 + runner 退出码 + 远端指标按下方三信号判红；网络类错误与 5xx 允许整轮重试一次pass / fail + 证据指针（runId、报告 URL、指标快照）非 0 退出码 / 空数据 → 判红；重试后仍失败即终局

判红信号怎么取判红条件说明
TestRun 终态.status.stage（枚举 initialization / initialized / created / started / stopped / finished / error）error → 红finished 只代表「跑完了」，不代表通过——只看终态会漏掉阈值失败
runner 退出码runner Pod 的 status.containerStatuses[*].exitCode非 0 → 红阈值未满足、脚本异常、运行期错误统一按「非 0 即红」处理，不区分具体码值（判定不绑定某个 k6 版本的码表）
空数据远端指标计数（k6_*）或 summary 里的用例 / 请求计数该 run 的请求数或用例数为 0 → 红（no_data=fail）专治「脚本跑通但什么都没测」这种最危险的假绿
环境不可达节点内对目标 Service 的连通性预检 + 首轮错误分类仅网络类错误与 5xx 允许一次重试，其余直接红重试次数固定为 1，避免把业务断言失败重跑成 flaky

1幂等

ConfigMap 与 TestRun 名都含 sha8：同 sha 重复触发先 get 再决定复用或重建；sha 变了就是新 run，不覆盖旧结果。重复执行不会产生第二份「同名不同内容」。

2并发

同一环境 + 同一服务只允许一个冒烟在跑（写路径套件必须串行）；锁用 K8s Lease 或复用环境锁思路，带超时自动释放，避免节点异常退出后死锁。

3超时与证据

节点超时（如 900s）> TestRun activeDeadlineSeconds（如 600s）。spec.cleanup: post 会删掉 runner 资源，与「判红要读退出码 / 日志」冲突 → 默认不开启，改为 TestRun 保留 7 天后清理。

三个必须在 test 集群实测一次、再写死进节点脚本的项：① runner Pod 的选择器口径（label 或 ownerRef）与退出码取法——先跑一次真实 TestRun 确认，别照抄臆测的 label；② spec.arguments 是字符串，带引号的参数（如 summaryTrendStats）写进脚本，环境相关值一律走 env / envFrom（示例见 §05）；③ --out experimental-prometheus-rw 的接收端与指标命名要先在 VictoriaMetrics 侧验通——当前 count({__name__=~"k6_.*"}) 是空集，「空数据判红」这条信号在验通前没有数据源。

05脚本来源四种方式与选型 路线 P 用 A（平台按 sha 取）；路线 C 用 D（集群侧自取）；B 是版本最硬的演进

方式做法代价版本可信度适用
A 平台按 sha 取脚本 推荐平台按 branch_id + commit sha 读取服务仓 perf/ → 生成 sha 命名 ConfigMap → TestRun spec.script.configMap 引用平台侧多一段取脚本逻辑；服务仓流水线零改动，300 仓立即受益中高（pin 到 sha）一期主干
B 服务 CI 产 OCI 制品服务流水线把 perf/ 打成 <acr>/<service>-k6:<git-sha>（与部署镜像同 sha）→ TestRun 用 spec.runner.image + spec.script.localFile要改平台托管的流水线模板（一处改动、全部仓生效）最高（镜像 digest 级）二期演进
C PVC 共享脚本脚本放 PVC，spec.script.volumeClaim 引用实现最简单不可用（脚本不随版本走）仅本地调试
D 集群侧自取 路线 C 用冒烟节点 Pod 内 git clone + fetch <sha>（只读 deploy key 走 Secret），或直接调 CodeUp OpenAPI 按 sha 取文件需要一个自带 git / kubectl / jq / k6 的 smoke-runner 镜像，外加 configmaps 写权限中高（pin 到 sha，且整条链路不经过平台）路线 C（不依赖平台）的主干

典型 TestRun（A 方式的形状；字段均来自实际 CRD 定义）：

apiVersion: k6.io/v1alpha1
kind: TestRun
metadata:
  name: member-service-smoke-6cf2c5b
  namespace: observability
spec:
  parallelism: 1                                  # 必填
  script:
    configMap:
      name: k6-scripts-member-service-6cf2c5b     # sha 命名，不可用浮动分支
      file: smoke/register.js
  runner:
    image: <acr>/k6-runner:1.3.0                 # 自建镜像：带 curl 的 starter + 业务依赖
    envFrom:
      - secretRef:
          name: k6-smoke-credentials              # 冒烟账号 / Token，只在平台侧
  arguments: '--env SERVICE_URL=http://member-service:8000'
禁止项：TestRun 引用浮动分支（main / test 最新）的脚本。门禁结论必须能回答「这是哪个 commit 的用例」——否则失败定位与复现都无从谈起。

07治理三件套 分散的代价必须一次性设计掉

1版本绑定

脚本 pin 到与部署镜像同源的 commit / digest；平台判红时记录该 sha。禁止浮动分支引用。

2覆盖率台账

定时扫各仓 perf/ + 结果表，产出「服务 × 环境 × 套件 × 最近一次结果 × 覆盖缺口」看板。这是把「分散」卖出「集中」价值的唯一补偿。

3时效口径

结果必须晚于该迭代分支最近一次 cd 成功；空数据 / 环境不可达 / 脚本缺失一律判红（no_data=fail）。

共享库怎么分发：k6 v2 不做包解析、依赖必须 vendored（loader-test/src/lib/vendor/k6-summary.cjs 即先例），所以 lib/http.ts、thresholds.ts、指标定义不能走 npm。做法是 版本化模板仓 + 各仓 templateVersion 标记 + 同步 bot 开 PR；k6.config.json 里的 templateVersion 就是给 blast-radius 用的，模板升级时能一次找出受影响的仓。

10风险与反模式 分散模型的七个必然退化点

风险规避方式
集群跑「默认分支最新脚本」，门禁结果对应未知版本TestRun 一律 pin 到 sha / digest；结果表记录该 sha
凭据散落到 300 个仓冒烟账号 / Token 只走平台侧 K8s Secret + envFrom；脚本只读 __ENV，仓内不出现任何密钥
共享库各仓各抄一版而漂移模板仓 + templateVersion + 同步 bot；k6 侧禁用 npm 分发
覆盖率与趋势不可见中心台账 bot 定时扫各仓 perf/，与结果表合并出看板
跨服务链路用例（下单 → 支付 → 履约）无处安放单独一个 perf-story 仓，别硬塞进任一服务仓
无平台路线下「没人消费结果」：冒烟跑完只留在指标里，门禁与发布单都不引用，等于人肉看板节点状态照常回写 branch_node（页面可见）+ VM 看板 + 覆盖率台账 bot；把「发布单引用冒烟记录」显式列为路线 P 的增项，而不是默认能力
反模式：每服务一个 k6 仓；把 UI 断言塞进 k6；把「全接口遍历」当冒烟；让冒烟脚本依赖生产数据；在 prod 用 k8s CronJob 做巡检；复用人工审批节点做「自动通过」。
