Critical（3 项）
  1. 明文生产凭据遍布 gitops：RabbitMQ / RocketMQ 四环境凭据、ES 生产密码、阿里云推送 appSecret、Redis 密码、腾讯云 SecretId/Key、美团 APP_SECRET，以及 ACR 仓库账号密码内联在渲染模板里。PASSWORD: 带字面量的 grep 命中约 348 / 684 个服务文件。argocd-repo-server 容器与每个 CI job 都持有生产数据面凭据；轮换需改动数十个文件且无审计。
  2. 密钥以普通 env var 下发，且「敏感」路径仍写明文进 manifest：敏感判定只匹配名字含 PASSWORD/SECRET，所以 TOKEN、ACCESS_KEY 类名称直接内联为字面量；即使走了敏感分支，生成的 Secret 用的是 stringData——明文照样进渲染产物。而 env var 对 kubectl describe/exec 可见，还会被 crash dump 与全程开启的 OTEL 链路捕获。
  3. 单个 clusterName.libsonnet 写错即部署到错误集群：这一行字符串决定制品分支、镜像仓库、域名、Pulumi 栈（即 IAC__* 凭据）、env 分支、Application 清单与 ArgoCD 目标分支。改成 prod 会让每个渲染产物指向生产端点与生产凭据，无任何对象级防护。引导脚本有严密的三方校验，但那只在引导时运行——普通提交 + 常规同步完全绕过它。雪上加霜：dev/test/staging 三个环境共用同一 git 分支。

逗号键语法：prod,prod-gray: '4301' 同时命中两个环境。-gray 环境会回退到基础环境取值，但 branch/enablePublicAccess/deploy/cronjobs 四个键刻意不继承——灰度 lane 必须显式声明才会部署。

三处静默歧义
  • 匹配到多个键时取字母序第一个且无断言 → prod: 与 prod,prod-gray: 并存时按字母序偶然决定。
  • 「是否环境选择器」的判定是启发式的 → 任何嵌套配置对象只要有字段名恰好叫 prod/test/default，就会被误判并塌缩为单一分支。
  • 环境判定完全依赖名称后缀 -gray → 一个正常命名恰好以 -gray 结尾的服务会被自动当作灰度 lane。

制品缺失即静默跳过：服务只在「可部署 ∧ 有制品 tag」时渲染。tag 缺失不报错，直接跳过整个服务——配合 ArgoCD 的自动 prune，一次 artifacts.libsonnet 合并事故就会静默删除该服务在生产的全部对象。而本地渲染脚本不聚合退出码，渲染失败仍返回 0。

02密钥引用机制 设计正确，但补丁层把明文写回产物

基础 cloudEnvs 由提交进仓库的 Pulumi 栈状态 JSON 派生：折叠资源清单，按 URN 尾部 {env}--{namespace}--{name} 三段命名解析，把资源类型映射为属性集（OSS、Kafka、ES、MongoDB、PolarDB、RAM、RDS、Redis、RocketMQ、腾讯 CAM/COS）。密码始终以 secretKeyRef 指针形式输出，真实值不进 manifest——这部分设计是正确的。

但补丁层破坏了该设计 cloudEnvsPatch 的条目会覆盖 cloudEnvs：
  • 名字含 PASSWORD/SECRET 的 → 换成 secretKeyRef，但字面量被聚合并以 stringData 写入一个真实的 Opaque Secret → 明文照样出现在渲染产物中。
  • 其余（TOKEN、ACCESS_KEY 等）→ 直接内联为普通字符串。
命名约定是承重的：Pulumi 资源名若 -- 段数不对，会从 cloudEnvs 中静默消失，直到渲染时报出「IAC key 不存在」。

整体优先级：IAC__ 补丁 > Pulumi 栈输出 > 报错。

CronJob 的「间隔 hack」 分钟字段被解析成秒；若 ≤300s，容器会跑无限 while true; ...; sleep N; done 循环而非一次性 curl——一个「永不退出的 CronJob」，靠 Forbid 防重。后果：该 pod 成了事实上的单例守护进程，无存活探针、无挂起检测、无 CronJob 失败信号；curl 失败只 echo 后继续（一次性路径会 exit 1）。命令还是字符串拼接且不转义，header 或 body 里的引号会破坏或注入 shell 命令。

平台 env 注入：每个容器都会被前置注入固定 env 块（NAMESPACE / APP / POD_NAME / POD_IP / CLUSTER_TYPE / OTEL 系列），用户 env 追加在后且 OTEL_URL 被过滤——所以用户不能覆盖 OTEL_URL 但可以遮蔽其它键（重复键，K8s 取最后一个）。

反亲和性不对称：Deployment/StatefulSet 得到真实的 required 反亲和；而 Rollout 的 required 变体被一个 && false 永久禁用，只剩 weight 100 的 preferred。

图 2 · 三套并行且正交的灰度机制

金丝雀门槛阈值正确，但闸门几乎无用
  • 成功条件是 len(result) == 0 || !(result[0] < 0.9999)——len(result) == 0 判定为成功。而默认规则给 canary 的权重是 0，且只有 17/684 的服务配了 rolloutSteps，因此绝大多数情况是「canary 完全没有流量」→ 分析永远通过；指标读取失败返回空序列同样通过。
  • 指标只统计 response_code!~"5.*" 在 40s irate 窗口内的比例 → 对延迟劣化、4xx 洪峰、连接重置、崩溃重启完全失明；低 RPS 下 40s 内的 0.9999 在统计上无意义。
  • maxSurge/maxUnavailable 均为 50%（发布期间可有一半实例不可用），而 revisionHistoryLimit: 0 意味着没有上一个 ReplicaSet 可回滚。

跨集群迁移权重：因 Gateway 与 Waypoint 各应用一次权重，实际比例是 W×(200−W)/100，所以配置值是反解出来的 W = ceil(100 − 10√(100−目标))。有断言强制「灰度先行」。另有一个手写的正则校验器逐字符检查括号配对与量词合法性，避免非法正则进到 Envoy。

05ArgoCD 同步策略 自动 prune + ignoreDifferences 掩盖漂移

  • 源：固定仓库、路径为命名空间名、递归、排除 *.app.yaml（它们是输入而非直接应用的清单）。
  • 目标分支：dev/test/staging → 'test'，prod → 'prod'——三个环境共用一个分支。
  • 同步选项：RespectIgnoreDifferences、PruneLast、前台传播、ApplyOutOfSyncOnly、CreateNamespace；ServerSideApply 仅对 observability 与 chaos-mesh 开启（因超大 CRD 会撞上注解 256KB 上限）。
  • 自动化：prune: true（仅 argocd 自身豁免）+ selfHeal: true。
ignoreDifferences 掩盖真实漂移 除了必要的 replicas 与 Argo header 路由外，还忽略了 Rollout 的整个 /metadata/annotations——而 sync-wave 与 configmap-md5 恰好就放在该注解 map 里。任何注解级变更（波次调整、手工 annotate、operator 写入状态）对 ArgoCD 永久不可见。配合 RespectIgnoreDifferences，这些排除对同步也生效，漂移永不被纠正。另有一段被注释的规则若启用，会让所有 HTTPRoute 的流量权重完全脱管。

       ├─ 制品分支 dev/test/staging/prod

       ├─ 域名 <cloud>-<type>.xlbsoft.com
       ├─ useAliIstio / useAlb（按版本号）
       └─ patchWorkload / patchArtifacts（dev/staging 复用 test tag）
  ├─ cloudEnvs ← Pulumi 栈 JSON → IAC__* 映射（被 cloudEnvsPatch 覆盖）

  ├─ services：扁平的「服务 → 集群内 URL」注册表（114 条）

  └─ routes-to-new-cluster：各应用迁移权重

引导脚本的六步安全闸门（这部分做得很好）：① 交互输入 clusterName 并对白名单校验；② kubeconfig 路径校验；③ 渲染 clusterName.libsonnet 必须与输入值一致（仓库状态须与操作者意图相符）；④ 从 kubectl 当前上下文提取 ACK 集群 hash，并以 Pulumi 栈状态中的托管集群 id 作白名单校验；⑤ 摘要表 + 生产环境需输入固定英文短语确认；⑥ clusterName 二次输入且两次必须一致。

但闸门只在引导时生效：一次针对 clusterName.libsonnet 的普通提交 + 常规 ArgoCD 同步就完全绕过它，且无 CI 断言校验分支的 clusterName 是否与其目标环境匹配。第 4 步的白名单还是用文本 grep 抓 Pulumi JSON，Pulumi 一旦重排或改格式即失效。

按服务制品分支模型：一个辅助脚本为某命名空间的每个服务文件派生一条独立分支，逐条 ff-only 合并后再汇总到 test。为何需要精确 refspec：macOS 默认卷大小写不敏感，而 git 松散引用是文件；本仓的制品 tag 与分支名大小写混用（如 i20260531 与 I20260729），两者会碰撞成同一路径导致 git fetch 报 ref 锁错误并污染整次 fetch。只 fetch 精确需要的引用即可避免。

图 3 · 巡检闭环与静默失效路径

Grafana Cookie 约 1 小时过期，而 cron 是每小时跑 GRAFANA_COOKIE 是必填环境变量并作为静态 session 头，无刷新、无服务账号、无 API token 路径。过期后抛错 → 被 CLI 的兜底 except 捕获 → 只记一行日志并返回 1；而 cron 把输出重定向到 /tmp，失败完全不可见——「没收到卡片」是唯一信号。结论：该巡检大部分时间处于失效状态。而它恢复后又会因读累计状态而报出一个「健康」的百分比（反映的是历史而非当前覆盖）。

其它设计细节：状态写入是原子的（写 tmp 再 rename），但 tmp 是固定同名兄弟文件，同命名空间并发运行会互相覆盖；json.load 无 try/except，文件损坏后每次运行都失败且唯一恢复手段是 reset（会丢弃数月累计）；覆盖率对比累计集合，故一旦见过即永久「已覆盖」——几个月前就坏掉的端点仍计入；无预设路径的服务会报 0.0% 而非 100%；卡片只有绿/橙两态，无红色失败态，且尽管状态里记了 last_seen 却没有陈旧度检查。

另有一处会直接导致不可用：crontab.example 里的路径缺了一级目录（少了 xlb/），照抄安装后会立即「No such file or directory」，且错误只写进无人查看的 /tmp 日志。同时它硬编码了某开发者的 $HOME。

  • M2 crontab.example 路径缺一级目录且硬编码个人 $HOME → 照抄即失败。
  • M3 环境取值的三处静默歧义（多键匹配取字母序、启发式误判配置对象、按名称后缀判定 gray）。
  • M4 -gray lane 默认继承生产凭据与生产端点 → 灰度金丝雀是全权限的生产客户端；配合 is-gray 头路由，任何能设该头的调用方都能到达它。

  • M6 跨集群迁移权重是手工维护的 433 行表，按 (namespace, app) 字符串相等匹配，typo 静默得到权重 0（流量悄悄不迁移）。表中已有一处数据缺陷：某应用名带尾随空格，永远无法匹配。双重路由补偿公式仅在 Gateway 与 Waypoint 都在链路上时才正确。
  • M7 1.27MB 的 CRD 大文件用客户端 apply（正是需要 ServerSideApply 的场景，但该选项只给了另两个命名空间）；dev/test/staging 共用一个 git 分支，本意给 dev 的提交下次同步就会到 staging。
  • M8 覆盖率语义可能读成假绿：无预设路径报 0.0%、累计对比使历史问题永久算「已覆盖」、卡片无红色态、记了 last_seen 却无陈旧检查；配置文件还允许把飞书凭据内联（直接值优先于环境变量引用），而 gitignore 只排除了 .env 与状态文件。

修复建议

  3. 渲染管线 fail-fast：制品 tag 缺失应报错而非跳过；本地渲染脚本聚合退出码；对「本次渲染对象数相比上次骤降」加门禁以防误 prune。
