# 文档格式规范（Documentation Format Spec）

> 本文件定义 XLB 零售平台仓库中 **所有总结类文档** 的编写与格式规范。
> Agent（及人工）在生成/更新任何总结类文档时 **必须** 遵循本规范。
>
> 本规范由仓库根目录的 `AGENTS.md` 引用而生效；本文件自身位于 `docs/文档格式规范.md`。

---

## 1. 适用范围

- **文档目录**：所有总结类文档统一存放于仓库根目录的 `docs/` 目录。
- **文档类型**：架构总览、服务清单、业务能力地图、技术栈、部署拓扑、集成与消息、专题分析等一切「总结 / 分析 / 说明」类产物。
- **不适用**：各子项目内部已有的 `README.md`、`docs/`、设计稿等由项目自身维护的文档；本规范只约束根 `docs/` 下的平台级汇总文档。

---

## 2. 输出格式：一律使用 HTML

- 所有总结类文档 **必须输出为 `.html`**，不使用 Markdown / PDF / Word 作为最终交付格式（本规范文件本身除外，它是规范说明而非总结类文档）。
- 每个 HTML 文档均为 **独立、可离线打开** 的静态页面（双击即可在浏览器查看，无需构建、无需联网）。
- **一律自托管**：JS / CSS 等资源全部放在 `docs/assets/` 下并以相对路径引用（Mermaid 已自托管，见 §7.1）。不引用外部 CDN——既避免断网/被墙失效，也消除第三方脚本供应链风险。
- 语言：**简体中文** 为主，专有名词 / 代码 / 服务名保留英文原文。
- 编码：`<meta charset="UTF-8">`，`<html lang="zh-CN">`。

---

## 3. 目录结构

```
docs/
├── assets/
│   ├── style.css              # 统一样式表（设计系统），所有文档共用
│   ├── mermaid.min.js         # 自托管 Mermaid v11（UMD）
│   └── diagram-init.js        # Mermaid 统一初始化与主题配置
├── 文档格式规范.md              # 本规范（由根 AGENTS.md 引用）
├── index.html                 # 文档中心首页（导航入口）
├── 01-architecture-overview.html
├── 02-service-catalog.html
├── 03-business-capabilities.html
├── 04-tech-stack.html
├── 05-infrastructure-deployment.html
├── 06-integrations-messaging.html
└── NN-<topic>.html            # 后续新增专题文档，两位数序号前缀 + 短横线命名
```

- **命名规则**：HTML 文档用 `两位数序号-英文短横线主题.html`（如 `07-data-flow.html`）。序号决定在首页与导航中的排列顺序。
- 新增文档时：① 在 `docs/` 下创建 HTML；② 在 `index.html` 增加导航卡片；③ 在所有文档顶部导航条 `.doc-nav` 中同步补充链接。

---

## 4. 统一样式表

- 所有文档 **必须** 通过以下方式引入共用样式，**不得** 内联大段 `<style>`：

  ```html
  <link rel="stylesheet" href="assets/style.css" />
  ```

- 样式表 `docs/assets/style.css` 是唯一的设计系统来源。需要调整视觉时 **改样式表**，不要在单个页面写覆盖样式。
- 颜色、圆角、阴影、间距等全部通过 `:root` 中的 CSS 变量控制。

---

## 5. 页面骨架（模板）

每个文档遵循统一骨架：**页头 → 导航条 → 主体（卡片分区）→ 页脚**。

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>文档标题 · XLB 零售平台</title>
  <link rel="stylesheet" href="assets/style.css" />
</head>
<body>
  <div class="doc-top">
  <header class="doc-header">
    <p class="eyebrow">XLB 零售平台 · 文档中心</p>
    <h1>文档标题</h1>
    <p class="subtitle">一句话描述本文档的内容与用途。</p>
    <p class="meta">最后更新：YYYY-MM-DD · 数据来源：源码静态分析</p>
  </header>

  <nav class="doc-nav">
    <a href="index.html">首页</a>
    <a href="01-architecture-overview.html">架构总览</a>
    <a href="02-service-catalog.html">服务清单</a>
    <a href="03-business-capabilities.html">业务能力</a>
    <a href="04-tech-stack.html">技术栈</a>
    <a href="05-infrastructure-deployment.html">部署拓扑</a>
    <a href="06-integrations-messaging.html">集成与消息</a>
  </nav>
  </div>

  <main class="doc-body">
    <section class="card">
      <h2><span class="num">01</span>分区标题</h2>
      <!-- 内容 -->
    </section>
  </main>

  <footer class="doc-footer">
    XLB 零售平台文档中心 · 本文档由源码静态分析生成，仅供架构参考。
  </footer>
</body>
</html>
```

- 当前页在 `.doc-nav` 中对应链接添加 `class="active"`。
- **`.doc-top` 包裹是硬要求**：`header.doc-header` 与 `nav.doc-nav` 的文字色是浅色（`#e2e8f0`/`#cbd5e1`），必须由 `<div class="doc-top">` 提供深色渐变背景（`style.css` 中 `.doc-top` 的 `linear-gradient(180deg,#0f172a,#1e293b)`）。漏写这个包裹时页头与导航会变成「白底浅字」，表现为「header 没有背景」「导航胶囊看不见」——已有 21–24 号文档踩过这个坑。

## 6. 组件与 class 约定

样式表已提供以下语义化 class，编写文档时 **优先复用**，不要自造 class：

| 用途 | class | 说明 |
|---|---|---|
| 页头背景容器 | `div.doc-top` | **必写**：包裹 `header.doc-header` + `nav.doc-nav`，提供深色渐变背景（漏写会导致页头白底浅字） |
| 内容分区 | `section.card` | 白底卡片，文档主体的基本容器 |
| 分区标题 | `h2 > span.num` | `num` 显示两位数序号 |
| **标题副标题** | `h2 > em` | 该节结论浓缩一句（如「8 回调端点 · 6 个走 Noop 空转」），扫标题即获得信息 |
| **目录** | `div.toc > b + ol > li > a` | 长文档（≥6 节）必备，双栏锚点导航 |
| 表格 | `div.table-wrap > table` | `table-wrap` 提供横向滚动与圆角边框；偶数行自动斑马纹 |
| 统计卡 | `.grid.cols-N > .stat`（内含 `.n` 数字 / `.l` 标签） | 关键指标展示 |
| **并列方案卡** | `.grid.cols-N > .mech.m1~m4`（内含 `h4 > span.num`） | 「N 套并行机制 / N 个模块对照」，带圆形编号徽章与独立配色 |
| **代码位置标注** | `div.loc` | 独立一行标注 `file:line` 或模块路径（等宽 + 弱化色），比内联 `code` 更易扫读 |
| 导航磁贴 | `.grid.cols-N > a.tile`（内含 `h3` / `p`） | 首页文档入口卡片 |
| 提示框 | `.callout` / `.callout.warn` / `.callout.danger` / `.callout.ok` | 重点/警告/风险/正向说明 |
| 技术标签组 | `.tags > span.tag` | 技术栈、topic 等短标签 |
| 架构图容器 | `div.diagram > pre.mermaid + p.arch-title` | Mermaid 图（见 §7）。**图注在图下方** |
| 泳道图 | `div.arch > div.lane > div.node` | 纯 CSS 分层图（见 §7.2） |
| 横向流程 | `div.flow > div.node + span.fa` | 纯 CSS 流程图（见 §7.2） |
| 代码 | `code` / `pre > code` | 行内与块级代码 |

> `.grid.cols-2/3/4` 采用 `auto-fit + minmax` 自适应（380/280/210px），列数随容器宽度自动收敛，无需额外断点。

### 徽章 `.badge`（用于标注类别）

- 技术栈：`.badge.java` `.badge.rust` `.badge.node` `.badge.rn` `.badge.mp` `.badge.infra`
- 状态：`.badge.ok`（自研/健康）`.badge.new`（新架构）`.badge.legacy`（遗留）`.badge.warn` `.badge.danger`

## 7. 架构图规范（必备）

**每篇 HTML 文档必须包含至少一张架构图**，帮助读者建立结构认知；纯文字与表格不满足要求。

### 7.1 首选：Mermaid（自托管）

- Mermaid 已**自托管**在 `docs/assets/mermaid.min.js`（v11 UMD，导出 `globalThis.mermaid`），初始化配置统一收敛在 `docs/assets/diagram-init.js`。
- 在 `</body>` 前按顺序引入这两个本地文件，**不要**在页面里重复写 `mermaid.initialize`：

  ```html
  <script src="assets/mermaid.min.js"></script>
  <script src="assets/diagram-init.js"></script>
  ```

- 需要调整图表主题/间距时，改 `diagram-init.js`（唯一来源），不要在单页覆盖。
- 升级 Mermaid：重新下载 `mermaid.min.js` 覆盖即可，无需改动任何 HTML。
- 图放在所解释内容的 `section.card` 内，用容器包裹，**图注置于图下方**：

  ```html
  <div class="diagram">
    <pre class="mermaid">
    flowchart TB
      A[member-weapp] --> B[xlb-mp-bff]
      B --> C[retail-new / oms-c]
    </pre>
    <p class="arch-title">图 1 · 系统分层架构</p>
  </div>
  ```

- 常用图型：`flowchart TB/LR`（分层/依赖）、`sequenceDiagram`（调用时序）、`stateDiagram-v2`（状态机）、`classDiagram`（类结构）、`erDiagram`（数据模型）。
- 语法避坑：`sequenceDiagram` 的 `participant ... as 标签` 与消息文本中**避免圆括号**，用 `·` 或 `=` 代替，否则部分版本解析失败。
- 断网降级：Mermaid 未加载时 `<pre class="mermaid">` 显示图源码，正文仍完整可读。

### 7.2 备选：纯 CSS 泳道图（离线场景）

样式表提供 `.arch`（分层泳道）与 `.flow`（横向流程）组件，节点配色与 `.badge` 语义一致：
`.node.java` `.node.rust` `.node.nodejs` `.node.rn` `.node.mp` `.node.store`（存储）`.node.mq`（消息）`.node.gray`（骨架/遗留/外部）`.node.hl`（强调）`.node.danger`（风险）。

### 7.3 通用要求

- 每篇文档 ≥ 1 张架构图；架构类文档（总览/拓扑/专题深读）建议按分区多图。
- ASCII 图（`pre > code`）只能作为辅助（如报文/时序细节），不能替代架构图。
- 图题统一用 `p.arch-title`，编号「图 N · 标题」。
- 同一事物在不同文档中的画法与命名保持一致（如服务名、层名）。

## 8. 内容规范

1. **可追溯**：结论应尽量给出来源（文件路径、`pom.xml`、`Cargo.toml`、`package.json`、`gitops` 定义等），使用 `code` 标注路径。
2. **必须标注分析基准（分支 / 提交）**：源码分析类文档**必须**在正文开头用 `.callout` 写明所分析仓库的 **分支名 + 短 SHA + 提交日期 + 与远端的领先/落后**。
   - 采集命令：`git -C <repo> rev-parse --abbrev-ref HEAD` · `rev-parse --short HEAD` · `log -1 --format=%cs` · `rev-list --left-right --count HEAD...@{u}`。
   - **不在 `prod` 分支时必须显式警示**（`.callout.warn` 或 `.callout.danger`），说明结论可能不代表生产。个人分支、feature 分支、落后远端、无上游跟踪均属此列。
   - 多仓合并为一篇时逐仓列出；仓库若不是 git 工作副本也要说明（结论来自内容而非签出状态）。
   - 理由：分支差异会直接改变结论的适用性——「模块仅骨架 / 无法编译」在个人开发分支上是正常的进行中状态，在 `prod` 上才是缺陷。
3. **准确优先**：当子项目文档与源码/构建文件冲突时，以 **源码与构建文件为准**，并在文中以 `.callout.warn` 标注差异（例如 `oms-plateform` 的 README 版本信息滞后于 `pom.xml`）。
4. **不泄露密钥**：严禁将 `.env` / 配置中的密码、AppSecret、密钥、Cookie、Token 等敏感值写入文档；只描述「存在该依赖」。
5. **中文业务术语**：业务能力使用团队惯用中文词（如 会员、优惠券、储值卡、拼团、抽奖、履约、逆向、结算、灰度）。
6. **时效**：每次更新在页头 `.meta` 写明「最后更新：YYYY-MM-DD」。
7. **无 JS 依赖**：允许少量原生内联 `<script>` 做交互增强（如锚点高亮），但页面在禁用 JS 时仍须完整可读。

## 8. 更新流程（Checklist）

新增或修改总结类文档时，依次确认：

- [ ] 文件放在 `docs/`，命名符合 `NN-topic.html`。
- [ ] 引用 `assets/style.css`；图表引入 `assets/mermaid.min.js` + `assets/diagram-init.js`，**无任何外部 CDN**。
- [ ] **本篇至少有一张架构图**（Mermaid 或纯 CSS 泳道图），图注 `p.arch-title` 在**图下方**，编号「图 N · 标题」。
- [ ] **源码分析类文档已标注分析基准**（分支 + SHA + 日期 + 与远端差距）；非 `prod` 分支已显式警示。
- [ ] 复用 §5 骨架与 §6 组件 class，未自造样式；页头已用 `<div class="doc-top">` 包裹 `header` + `nav`（漏写会导致页头白底浅字、导航不可见）。
- [ ] 分区数 ≥6 时已加 `div.toc` 目录，且各 `section` 有 `id` 锚点。
- [ ] 每个 `h2` 尽量带 `em` 副标题浓缩本节结论。
- [ ] 页头 `.meta` 更新了「最后更新」日期。
- [ ] `index.html` 与各文档 `.doc-nav` 已同步新增链接。
- [ ] 未包含任何敏感凭据。
- [ ] 浏览器本地打开显示正常、无控制台报错、移动端可读。
