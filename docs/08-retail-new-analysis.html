旧结论最新 prod 实测判定
C-2 券库存扣减 UPDATE 无余量守卫、不校验受影响行数 → 可超发 库存模型已重构为 coupon_type_stock / coupon_type_share_stock（新增 total/usable/shared 三段）。但扣减语句仍无守卫：SET usable_stock = usable_stock - #{delta} WHERE coupon_type_id = ?，WHERE 中没有 AND usable_stock >= delta → usable_stock 可扣成负数。另外用 <foreach separator=";"> 多语句执行，需开启 allowMultiQueries，本身也是风险面。 仍存在
C-3 拼团 TCC 在 Confirm 阶段执行业务写 仍存在，且实现已换成 Seata（BusinessActionContext / xid，全仓 7 处 @TwoPhaseBusinessAction）。commit()（即 Confirm）内仍有：远程调用 groupService.payConfirm、DB 写 pickupOrderService.updateBatchStatusByIdAndStatus、ES 写 esPushService.pushOrderSync/pushPickupOrder。Confirm 失败仍不可回退。 仍存在

对比：oms-plateform 已改用事务消息，本仓尚未跟进。		 仍存在
High 用随机 sleep 代替幂等键 OrderServiceImpl 中 Thread.sleep(RandomUtil...) 已移除 已修复

52 个 Maven 模块 现为 53 个 已变化
最重要的架构变化：分布式事务改用 Seata 旧版描述的自研 TCC（*TccService 手工 Try/Confirm/Cancel）已迁移到 Seata TCC（@TwoPhaseBusinessAction，7 处），配置见 oms-c/src/main/resources/application.yaml:246。

但迁移并未修正语义问题——Confirm（commit()）阶段依旧承载远程调用与业务写。Seata 的 Confirm 同样要求幂等且不应失败，因此该缺陷在新框架下风险不变甚至更高（Seata 会重试 Confirm，重复的 ES 推送与状态更新会被放大）。

结论 本仓在这一个月的迭代中修掉了随机 sleep、重构了库存模型、引入了 Seata，但三项 Critical/High 核心缺陷（库存无守卫、Confirm 写业务、无 outbox）以及大面积鉴权旁路均未处理。这与 07 篇（oms-plateform）的情况相反——那边补齐了事务消息与死信队列。建议把 oms-plateform 的可靠性做法反向移植到本仓。

1事件先于落库

MQ 发送早于 DB 提交，事务回滚后消息已投出，下游收到不存在的订单。无 outbox、无 AFTER_COMMIT 监听。

2随机 sleep 代替幂等

用随机休眠规避并发冲突，而非以幂等键收敛——高并发下仍会重复，且拉长事务持有时间。

GroupTccService 在 Confirm 里执行业务写入，Confirm 失败无法回退且不可重放，破坏 TCC 契约。

3.2 事件监听器

核销事件 OrderWriteOffEvent 由 PickupWriteOffConsumer.java:50 发布，4 个同步监听器订阅（含两个会发 MQ 的）。任一监听器抛异常都会让整条核销消费失败并重投，而先前监听器的 MQ 已经发出 → 重复发放双倍积分与公益积分。

另有性能缺陷：DoublePointListener.java:61-63 与 PointPublicWelfareListener.java:52-54 在循环内重复构建同一个与循环变量无关的分组 Map；前者还在循环内对全量明细执行 checkQuantity（应为当前退单明细）。
