05触发原因：配置变更与规则叠加 20:08 的灰度匹配 + 既有的 100% 切流 + 过宽的 baggage 规则

生产路由（gitops prod 分支）对 wms 的切流配置：

repos/gitops/apps/routes-to-new-cluster.libsonnet:450（origin/prod 83266bda）
{ namespace: 'wms', app: 'wms',
  grayToNewClusterFrom0To100:   { staging: 100, prod: 100 },
  normalToNewClusterFrom0To100: { staging: 100, prod: 1 } }

含义：灰度流量 100% 去新集群、普通流量 1%；模板还对「普通权重 > 0 必须先灰度到 100」有断言 （HTTPRoute.libsonnet：assert rawNormalWeight == 0 || rawGrayWeight == 100），也就是说灰度这条路是设计上「全量切新集群」的开关。

20:04–20:08 的三笔变更改变了「谁算灰度」：

repos/gitops/apps/wms/wms.app.yaml · routeToGray（origin/prod）
routeToGray:
  dev:
    - headers: [{ name: "company-id",   type: "Exact",            value: "1001" }]
    - headers: [{ name: "user-id",      type: "RegularExpression", value: "^(100100000617|6666600128890)$" }]
    - headers: [{ name: "warehouse-id", type: "RegularExpression", value: "^(6655500039844)$" }]
  prod:                                    # ← 10-15 20:05/20:08 新增
    - headers: [{ name: "company-id",   type: "Exact",            value: "1001" }]
    - headers: [{ name: "user-id",      type: "RegularExpression", value: "^(100100000617|6666600128890)$" }]
    - headers: [{ name: "warehouse-id", type: "Exact",            value: "6655500039844" }]
两处放大器同时生效
  1. 灰度 → 100% 远端：renderPreRules 对灰度规则按 grayWeight 改写后端，grayWeight=100 时等价于 localBackendRefs(0) + remoteBackendRef(100) —— 灰度的语义在这里不是「小流量验证」，而是「整批换集群」。 本次被纳入灰度的是 company-id=1001 等条件，覆盖的是整批真实生产客群，不是内部白名单。
  2. baggage-to-remote 抢跑：模板对 baggage 任意非空值的匹配规则不校验 Host 权重，命中后 100% 转发远端 （matches: headers baggage =~ .+，backendRefs 只有 remoteBackendRef{weight:100}）。 模板注释本身已给出警告：必须让 gray-baggage 排在它之前，否则「携带 baggage 的灰度请求会被'任意非空 baggage 全量转发新集群'抢先命中」； 而 gray-baggage 仅在 136 及以上集群生成（老 prod 不生成），所以老集群上这条保护缺位。
仍是推断的部分（未取得 136 侧遥测）
  • 「baggage 头为何在 20:19 同时放量、且归零时间与 wms.wms.2（20:38）不一致」——本数据源只覆盖 prod 老集群， 无法看到新集群侧与泳道/灰度标记的生成端；从代码路径看，最合理的解释是灰度标记经 W3C baggage 透传后被过宽的 baggage 规则整批命中（见上图 2）。
  • 「20:58 归零」是标记面不再命中、还是远端被修复，两者在本数据源内不可区分（归零后远端既无 503 也无 200，倾向于前者）。

08为什么会出现「同一域名一部分通、一部分 503」 同一 hostname 上并存本地规则与远端规则，命中面由请求头决定

  • wms.wms 同时挂在 wms 的 HTTPRoute 上：默认规则指向本地 wms Service，跨集群规则指向 ack-136-ingressgateway-inner-ips。
  • 命中哪条由请求头决定：baggage 非空 → 远端；命中灰度条件（company-id / user-id / warehouse-id）→ 灰度规则 → 远端（权重 100）。
  • 因此同一个域名、同一批接口，会出现「大部分 200、一小部分稳定 503」，且503 的分布与客户端/仓库/客群强相关，而不是按时间随机分布（本案例的 503 集中在 RN 端与特定客群即为此表现）。
  • 反过来，收到 503 的终端会重试，进一步把远端请求量推高（本窗口远端请求量约为本地同时段的数倍），放大故障观感。

09修复建议与遗留问题 先给切流加「远端可用」门禁，再收紧 baggage 匹配

P0 · 切流前必须校验远端可服务
  • 灰度权重 gray=100 是「整批客群换集群」的开关，当前没有任何「远端健康才放量」的门禁：本次远端 503 期间，权重照旧为 100，失败持续到匹配面自己消失。
  • 建议在灰度放量流程中加入远端探活（对目标 host 的健康接口或金丝雀请求）作为前置条件；远端不可用时自动回落本地权重，而不是让 URX 把失败透传给终端。
P0 · 收紧 baggage-to-remote 的匹配面
  • 现状：baggage =~ .+ 即 100% 远端，且老集群不生成 gray-baggage 兜底 → 任何透传 Sentry/OTel baggage 的调用都可能被整批送走，与权重设计完全脱钩。
  • 建议：改为只匹配显式泳道标记（如 baggage 中的 <base>.<ns>=<lane> 或专用头 x-cross-cluster），或按 Host 限定；并补齐老集群侧的灰度 baggge 规则顺序约束（或在不生成该规则时禁用宽松匹配）。
P1 · 可观测性与告警口径
  • 远端转发流的日志标签把 namespace/svc 记成 upstream cluster 的归属（istio-system / ack-136-ingressgateway-inner-ips），导致「按目的服务名查 503」为盲区；建议在标签派生里保留真实目的服务（authority / destination_service）。
  • 增加跨集群转发失败率的直接告警（route_name 维度的 5xx），不必依赖 success_ratio 间接暴露。
  • routeToGray 这类「影响谁算灰度」的变更应带变更人/变更单/生效范围到看板，缩短「配置变更 ↔ 流量异常」的关联时间。
P2 · 存量残留
  • wms.wms.1 持续约 14–15 次/小时 503（贯穿 10-15 全天与 10-16），10-16 09:00 小时桶出现 172 次尖峰 —— 同一条远端路径仍有零星不可用，建议单独定位（可能是探活/定时任务类调用）。

本次排查的可复用要点
  1. 「某服务访问不通」先区分目的地（老集群 / 新集群）而不是先看应用指标：本例本地应用指标几乎无异常。
  2. 域名既是「内网服务名」也是「HTTPRoute hostname」时，两个集群的同名路由会共存；按 authority 查证比按 namespace+svc 更可靠。
  3. response_flags=URX + 有 upstream_host + 百毫秒级 upstream_service_time = 远端主动 503、重试耗尽，可直接排除网络不可达与超时。
  4. 反向代理（rustyproxy）只在上游非 2xx 时打印 status … : target_url，这条日志是「用户可见失败」的第一手证据。
