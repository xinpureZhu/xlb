Critical（4 项）
  1. 小程序上传私钥提交进 Git：微信 ×2 + 支付宝 ×1 的 .key 文件均被跟踪，.gitignore 未包含 key/。任何有仓库读权限的人可直接以生产 appid 上传/发布小程序代码版本——等同于生产环境代码执行权。
  2. 私有 npm registry token 提交进 Git：可读写公司私有包 → 供应链投毒（往共享组件包发一个恶意版本，会被所有 App 与 BFF 构建拉取）。
  3. 热更新平台账号明文口令写在脚本里（含明文密码、可反查的 MD5、以及一枚有效期内的 JWT）→ 控制该账号即可向两个 App 下发任意 JS bundle，全量用户 RCE。
  4. 远程 bundle 无任何完整性校验：iOS 从 OSS 下载 host 主 bundle 直接落盘执行——无签名验签、无 hash 比对、无证书 pinning；JS 侧拉取全部 remote 容器同样未配验签；版本清单自身也是无签名的明文 JSON。任何能写该 OSS bucket 或劫持 HTTPS 的人 = 全量客户端任意代码执行。加重项：bucket 名字面意思是「临时仅用于测试」，生产链路却依赖它，且 host 与所有 remote 共用同一 bucket。

双向联邦的耦合风险 host 只 expose 两个模块，但其中 WebViewPage 是一个 1189 行的上帝组件，内嵌 30+ 个 JSBridge 能力（扫码、上传、定位、打印、PDF、IM 弹窗、地图、方向锁定），import 面覆盖十余个原生模块。expose 它等价于把 host 的半个运行时变成对外 API 契约。而两者是独立发版的，且双方都设 dts: false——host 侧任何重构都会静默打断已发布的 remote bundle。

错误处理三层但每层只是打印：MF runtime plugin 仅 console.warn；FallbackComponent 把 error.message + error.stack 红字渲染给终端用户；remote 内部的 NotFound 甚至把全部可用组件名列表打印出来。全链路无重试、无超时、无降级到上一缓存版本、无上报（Sentry 已引入但未接此链路）。

02shared 依赖不对称 实测 host 52 项 vs remote 34 项

shared 由一段递归扫描 node_modules 找 *.podspec 的代码计算——动机正确（含原生代码的包在 App 二进制里只有一份实例，必须 singleton），但该代码在 host 与各 remote 间是复制粘贴且配置体不同。实跑比对结果：

已存在真实的 major 级版本差异
  • react-native-screens：host 4.11.1 vs erp/mem 3.25.0。3.x→4.x 导出面变化很大（enableScreens、header config props、Fabric 组件名）。运行时生效的是 host 的 4.11.1，而 remote 的 JS 是按 3.x API 编译的 → undefined is not a function / native view manager 找不到 → 白屏或 crash，且只在特定 remote 的特定页面触发。
  • react-native-pager-view：mem 6.2.3 vs host 6.8.1；safe-area-context：5.4.1 vs ^5.5.0。
  • 两侧均未设 strictVersion，remote 侧连 version 都不填 → MF 无法版本协商，连 warning 都不会给。
  • 属于跨仓库远程触发的回归：host 单独发版就能改变 remote 的运行时依赖，无法在任一仓库的 CI 中发现。

foca 不共享的后果：host 的鉴权状态是 foca model 并以 props 注入 remote，但 remote 自己也 import 了 foca 并在其 http 层读取——由于 foca 不在 remote 的 shared 里，remote bundle 自带一份 foca runtime + 一份独立的 auth model，两套 store 互不同步。代码靠 global.authModel || defineModel(...) 这种全局变量兜底桥接，属 hack 而非机制保障。后果是 token 刷新只更新 host 那份，remote 仍持旧 token → 间歇性 401。

此外 remoteApps.ts 的 importFn 用 Promise.all([...大量 import...]) 手工模拟 shared 预热（base 预加载 21 个包）——正是因为 shared 集合不对称，只能靠 host 显式 import 把原生模块拉进 host 图再供 remote 消费。新增 remote 依赖时必须同步改 host 代码。

03Bundle 解析与灰度 灰度机制实为死代码

解析顺序：① DEBUG 且 localhost 可达 → Metro；② 拉 OSS version.json 取分支版本（最多 300 次重试 × 1s）；③ 本地缓存命中即用；④ 下载并缓存。JS 侧类似，但 platform 写死 ios（Android 走同一路径会取到 iOS 产物），且代码里还留着 debugger; 语句。

灰度机制是死代码 getBundleRoutesPromise 会 fetch OSS 的 bundle-routes/v1.2.3.json，但把结果赋值后完全丢弃，转而 return 一个硬编码字面量——里面把两个员工 userId 与 prod/prod-gray 的 bundle URL 写死在客户端源码里。而该 Promise 在整个仓库中再也没有被 await 或引用过。

结果：灰度既不可运营配置，当前也完全不生效（每次启动仍白发一个无用的 OSS 请求），实际路由 100% 走 version.json 分支。

对照：member-weapp 的灰度实现成熟得多——规则从 OSS 动态拉取，支持手机号后缀匹配与门店白名单，末条无规则项作为默认。RN 侧完全没有对齐这套能力。

版本清单格式：{"<repo>": {"<branch>": "<datetime>-<branch>-<sha>"}}，仅保留 dev|main|prod|staging|test 前缀分支。但客户端只读 .main——prod/staging 分支在 manifest 里写了却从不被读取，环境隔离形同虚设。

06member-weapp 小程序 多端适配靠编译期字符串替换

  • 多端适配三处协同：① defineConstants 把全局对象名换掉（wx → my）——这是编译期字符串替换，让业务代码里裸写的 wx.xxx 在支付宝下变成 my.xxx；很脆，因为两套 API 并非同名同签名，替换后只是编译通过。② 支付宝时注入适配插件。③ 插件把 navigationStyle: 'custom' 翻译成支付宝的透明标题配置，并强制所有页面禁用回弹。另有 3 个 patch 打在 Taro 上，说明官方适配层不够用。
  • 路由：568 行 ROUTE_MAP + 11 个分包；统一中转页设计（分享/扫码/活动都先落 entry 再分发）；主包体积治理（optimizeMainPackage + .main 后缀排除）。
  • 状态：纯 zustand v5，17 个 store + tabBar 独立 store，统一 createSelectors 包装以获得细粒度订阅。但 store/index.ts 又尝试 slice 模式且只挂了一个 slice——两种组织方式并存。
  • API 层：3 个拦截器（业务码 / HTTP 状态码 / Header 注入）。Token 刷新用 isTokenRefreshing 标志 + 失败队列做并发合并（比 auth-server 的无防护做得好）。断网做一次重试并按 Map 去重。
  • 存储明文：token/userInfo/openid/unionid/companyid 全部 setStorageSync 明文。
  • 自定义 tabBar：图标全走 CDN 而非本地资源（省包体但首屏依赖网络）；中间「会员码」是无图标凸起位；用防抖处理「每个页面都有一个 tabBar 实例」的去重问题。另存在 customize-tab-bar 双份实现。
安全配置放松 project.private.config.json（已入库）设 urlCheck: false 关闭域名白名单校验，与生产行为不一致，容易把未报备域名的调用带上线。.env.production 内含腾讯地图 key 等（前端 key 泄露风险相对可控，但未做 referer/签名限制时会被盗刷配额）。

07OTA 与发布 pushy 通道已停用但凭据仍在仓库

1第一代（遗留单体 · pushy）

update.json 含 iOS/Android 的 appId+appKey（已入库）。发布脚本链路：登录 → 选 App → bundle → publish（正则从 stdout 抠 versionId）→ 绑定（当前被注释）。CI 为单 stage 手动触发。

脚本里明文写着平台账号口令，另一处还有可反查的 MD5 与一枚有效期内的 JWT。

2第二代（自研 CDN 分发）

react-native-update 依赖与含 appKey 的 update.json 仍在，但 JS 侧已被彻底掏空（import 整行注释、组件 render() 直接返回空）→ pushy 通道事实上已停用，凭据却仍在仓库里。

实际生效的是 create-version.js → version.json → OSS → 客户端拉取。仓库内无 CI 定义，脚本依赖的环境变量契约无处校验，缺失时会生成 undefined-undefined-undefined 版本串。

小程序发布：交互式 4 步（选平台 → 选环境 → 选版本升级类型 → 确认），bump 版本号并 git commit，然后 build。但存在两个缺陷：① 取消判断写错——prompt 的「取消」返回字符串 'no'（truthy），选取消也会继续构建并提交版本号；② 只 build 不 upload，而版本号已 bump 并 commit → upload 失败或遗忘则本地版本与线上永久错位，而支付宝不允许同版本重复上传。
