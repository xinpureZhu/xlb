贫血模型 vs 充血模型

同一个业务，两种放行为的方式：对象是只有数据的「名词」，还是自带行为与规则的「活物」。

01一句话区分数据与行为是否住在同一个对象里

A贫血模型 Anemic

领域对象只有数据和 getter/setter，本质是个结构体 / 记录。所有行为住在对象外面：Service、Manager、Controller，甚至界面脚本。 对象是名词，动词由别人对它实施。

B充血模型 Rich

领域对象自带行为，行为里守着不变量（业务规则）：想改状态，只能调它的方法，而方法保证规则不被破坏。 对象是活物：你对它说意图，它自己完成并自检。

维度贫血充血
对象内容字段 + getter/setter字段 + 业务方法
行为住在哪外部 Service / 调用方对象自己的方法
不变量谁守每个调用者各自「记得」守 → 迟早有人忘方法内部守，绕不过
规则归属感同一条规则在 N 个调用处复制 N 遍唯一归属，改一处生效
换界面 / 换入口流程埋在调用方，换入口 ≈ 重写流程入口是薄壳，可整体替换
可测试性要拉起 Service 栈 / UI 才能测规则new 一个对象即可单测
阅读体验看对象不知道它能干嘛，要追 Service读对象即读业务
先说明：贫血不是原罪。简单 CRUD、一次性脚本、事务脚本风格的小服务，贫血更直白。 它变成问题是当规则多、调用方多、生命周期长时——规则散落的代价随调用方数量线性放大。

贫血的典型症状：对象删掉所有 getter/setter 后不剩任何业务信息；Service 越来越胖； 同一条 if 判断在多个文件里出现；界面或控制器里藏着「先 A 再 B、失败记得 C」的流程知识。

  participant C as 调用方

图 4 · 充血时序：规则收进对象，任何入口都走同一条受守的路

充血的判定标准很简单：把对象 new 出来，不连数据库、不拉起框架，就能用单测跑通核心规则。 能做到，说明规则真的住在对象里。

04三问自检你的代码是哪种

1删掉界面和控制器

业务规则还在吗？如果规则跟着 UI / Controller 一起消失，说明它们是贫血甚至 Smart UI。

2第二个入口

加一个新入口时，需要「记得」复制哪些校验？需要复制的清单越长，贫血越重。

3最小单测

测一条核心规则要启动几层？层数即规则被埋的深度。

怎么选：规则少、入口单一、寿命短 → 贫血足够，别过度设计。规则多、入口多、要换 UI 或长期演进 → 把动词和不变量搬回对象（充血），让入口变薄——这是「换界面不重写业务」的前提。
