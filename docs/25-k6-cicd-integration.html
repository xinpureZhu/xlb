01结论与判据 冒烟是主干、压测是按需层；自动触发靠既有编排、不靠人点按钮

结论：k6 的价值大头在日常、自动触发的业务冒烟，压测只是其中一小块。落地方式是把 3 个既有机制拼起来： 执行复用已装在 test 集群的 k6-operator（repos/gitops/apps/observability/grafana-k6/）； 触发与阻断复用 Argo 环境子流程 + efficiency 的 /callback/execute job 注册表（新增 job_type=smoke）； 留痕与发布卡点复用坚果 / quality-portal 现有检查项与发布单 fail-closed 链。
4自动触发方式：部署后 / 晋级前 / 定时巡检 / 平台手工
0需要的人点按钮：判定由 k6 断言驱动
1次采集三处消费：节点判定 / VM 指标 / 门禁报告

四条判断依据：

  1. 现有的「冒烟」不是自动化测试：Argo 环境流程里的 smoke_test 是人工审批节点（ApprovalNodes 白名单 + approval-polling 模板，14 天超时），efficiency 里唯一的「自动完成冒烟」能力 auto-complete-smoke-node 完成的是飞书项目工作项节点，不是 Argo 节点（config/feishu.go:34-38、pkg/jianguo/feishu_node_completion.go）。所以「日常自动触发的业务冒烟」目前不存在，需要新建。
  2. 自动触发不需要新平台：Argo pod 已经会用公开无鉴权的 POST /api/v1/workflow/callback/execute 触发 CodeUp 构建（job_type=pipeline / action=trigger_ci，cicd-node.yaml:68-74 → job/adapter_pipeline.go:175-200）。测试任务可以用同一条通道：新增 job_type=smoke。
  3. 不要劫持人工审批节点：smoke_test / test_verification / product_verification 的放行只能走私有鉴权路由 POST /api/v1/workflow/approval/submit（JWT + Casbin），公开的 /workflow/node/complete 会话不校验审批状态。正确做法是在 cd 之后新增一个自判定的 smoke-gate 节点，人工审批节点保持原样（业务确认），两者职责不重叠。
  4. 质量平台的执行计划不是量测口径的合适容器：case_execute_plan/case/case_result 无环境维度、无「接口/UI/自动化」类型标记，用例来自 quality-case 自带用例库，写结果要走飞书 OAuth 的 JWT 会话（AuthCheck + AuthService.login(code)）；且 通过率不落库（读时按 latest_execute_result 计算），quality-metric 又按 first_execute_result 统计——同一批数据两套口径。贸然写入会制造第三套口径。
两条落地路线：§08 平台内（进环境子流程与发布单，能力最全，需 efficiency 改动）；§09 独立于效能平台（资产全在 repos/gitops/apps/ + Argo + k6-operator，零 Go 改动、1–2 周可上线，但进不了发布单）；§10 给出逐维对比与「先用独立平面拿到能力、再把结论桥接进平台拿口径」的混合落地顺序。
反向结论（不推荐）：① 不要把 k6 只放在服务仓的 CodeUp 流水线里 —— 那是构建期，看不到部署结果；② 不要为冒烟新建独立测试平台 —— 执行、编排、门禁、观测四处都已存在；③ 不要把「自动通过」做成自动调用审批接口 —— 那会绕过人工审批语义，且公开路由不校验审批状态，等于把门禁交给任何集群内进程。

04现状：冒烟与自动化测试资产 有「冒烟」这个词，但没有自动跑的冒烟

A飞书「冒烟测试」节点（人工 + 条件自动完成）

efficiency 可在坚果准入通过后自动完成飞书项目工作项的「冒烟测试」节点（auto-complete-smoke-node，默认关闭；实现 pkg/jianguo/feishu_node_completion.go，按名称或 state_key 定位节点，无负责人时改发飞书卡片找人工）。

这是「准入通过 → 手动节点的自动化」，与「自动跑一遍业务功能」无关。

Bquality-case 执行计划（人工填报为主）

5 表模型：case_execute_plan（按 (story_id, type) upsert）→ case_execute_case（uk_execute_plan_case，存 latest_execute_result）→ case_execute_result（append-only 历史） + _bug / _attachment。

计划类型按需求自动生成 5 份：DEVELOP_SMOKE/TEST_SMOKE/TEST/STAGING/UAT；用例取自 quality-case 用例库（case_node）并按 case_story_case 收窄。无环境维度、无接口/UI/自动化类型标记。

C结果写入与统计口径

唯一写入口：POST /quality-case/execute-plan/{plan_id}/result（ExecutePlanController:64-70），鉴权是 AuthCheck 强制的 Authorization JWT（RS256 + sys_auth 会话，登录需飞书 OAuth code）；没有静态 token 或 @NoAuth 写入端点，也没有外部结果摄取任务。

通过率不落库，读时按 latest_execute_result='SUCCESS' / 非空计数计算；TEST_SMOKE 结果会同步到 TEST，STAGING 结果触发迭代回归计划创建（ExecutePlanListener）。quality-metric 读同一批表但用 first_execute_result —— 两套口径。

06冒烟与压测：两类测试的工程差异 同名工具，不同工艺

维度业务冒烟（主干）压测 / 容量（按需层）
回答的问题「这条业务链路现在还能走通吗」「在 X QPS 下会不会劣化」
断言对象业务语义：业务码、状态机流转、字段一致性、幂等、金额/库存守恒耗时分布（P95/P99）、错误率、吞吐、饱和度
失败含义功能缺陷或环境不可用 → 立即阻断容量不足或劣化 → 阻断晋级 / 触发容量动作
频率每次部署后、每次晋级前、定时巡检（可达每天多次）发布前按需、 nightly、大促前阶梯
时长预算目标 < 5 分钟（小集 < 2 分钟）分钟级到小时级
压力模型低并发、少样本（1–5 VU，几条到几十条链路）constant-arrival-rate 目标 RPS，多 VU
数据要求可重复、可清理、幂等；写路径优先用专用账号/沙箱数据数据量级要能反映真实分布，需造数与清理方案
环境dev / test / staging（部署后自动）test / staging；prod 不压测
对环境的干扰低（但要避免写脏数据）高（需环境互斥与窗口）
为什么必须分开设计：冒烟是高频、低频次压力、强断言，压测是低频、高压力、弱断言强指标。把二者塞进同一个脚本/同一个门禁，会出现「冒烟把环境压出噪声」与「压测断言写不出业务缺陷」的双输。

S3 冒烟结果入账：两条路线，推荐前者

Aefficiency 侧自建（推荐，本仓可控）

新增静态 token 的机机接口（如 POST /api/v1/workitem/smoke/result）+ 结果表（work_item_id / iteration_branch_id / service_id / environment / suite / passed / total / failed / executed_at / report_url），并在 release_quality_report 的就绪判定里作为一个新来源与现有 jian_guo_gate_records 并列。

优点：无需飞书 OAuth 会话、无伪用例、口径由我们定义、可在 prod 分支直接实现；缺点：报告不在质量平台聚合页，需与质量团队对齐口径表述。

B写 quality-case 执行计划（口径对齐，跨团队）

把冒烟套件登记为 quality-case 用例库里的「伪用例」，机器执行人通过 POST /execute-plan/{plan_id}/result 提交 SUCCESS/FAIL/BLOCK，从而复用现有 DEVELOP_SMOKE_CASE/TEST_CASE/STAGING_CASE 检查项与聚合报告。

代价：需要服务账号的飞书 OAuth 会话（JWT 与 sys_auth 会话绑定，需刷新）；用例库被自动化伪用例污染；无环境/服务维度；与 quality-metric 的 first_execute_result 口径不一致。适合作为二期「口径统一」议题，不适合作为一期主干。

发布单校验只在提交时做一次快照（ReleaseOrderValidityTime 默认次日 06:00 失效；范围变化抛 RELEASE_SCOPE_CHANGED），且发布动作不再复查报告。因此冒烟结果必须有时效口径：结果时间必须晚于该迭代分支最近一次 cd 成功。

P 按需压测（降级为独立层）

  • 沿用现有 k6-operator + 压测脚本（constant-arrival-rate + 目标 RPS），触发方式为发布前按需 / nightly / 大促前阶梯；不进入「每次部署后」路径。
  • 阈值与基线见 §12；结果同样归档并写 summary，供容量报告与趋势面板使用。

G prod 灰度指标门禁（不跑 k6）

  • 扩展 istio-success-rate AnalysisTemplate：新增 P95 延迟 metric（现仅 5xx 比率），作为 analysis.templates[] 第二项。指标可用性已实测：prod 观测后端存在 istio_request_duration_milliseconds_bucket（645,720 条序列）与 istio_requests_total（32,965 条）。
  • prod 不压测、不冒烟打真实业务写路径；生产性能风险由灰度真实流量 + 指标门禁吸收。

关键洞察（决定这条路可行）：阻断不需要平台配合。Argo Rollouts 的 AnalysisTemplate 已支持 Job provider（repos/gitops/apps/argo-rollouts/crd.yaml:3935，Rollouts 版本 test-v1.9.0），每个命名空间的 Rollout 已经挂了 analysis.templates[]（templates/App/Workload.libsonnet:234-256）。用 Job provider 跑 k6 冒烟：AnalysisRun 失败 → Rollout Degraded → efficiency 的 cd 节点本来就在轮询 Rollout 状态（Degraded 是它已识别的首个 CD 失败信号）→ 环境推进被阻断，全程不新增/修改 efficiency 代码。

这条路的定义：不调用 efficiency 的任何 API / DB / 工作流，不自建平台服务，全部资产声明在 repos/gitops/apps/（ArgoCD 同一套 Application 渲染 <ns>/**/*.jsonnet），由 Argo + k6-operator + VictoriaMetrics + Alertmanager 承载「执行—判定—阻断—通知」。

11冒烟用例工程规范 断言业务语义 · 可重复可清理 · 5 分钟内出结论

1分层与范围

每服务一个 service-smoke 集（该服务对外接口的核心正向 + 关键异常分支）；跨服务用 story-smoke（需求链路，如「下单 → 支付 → 履约」）与 env-gate（环境级基础依赖：网关、鉴权、配置中心、MQ 可达）。三层共用 runner，按触发场景选择集。

2断言口径

禁止只断言 HTTP 200。必须断言：业务码（code=0 之类）、关键字段（订单号/金额/库存）、状态机（创建→支付→完成，或失败态）、幂等（重复请求不产生第二笔）、可观测副作用（查询接口能查到刚才写的数据）。

3数据策略

专用冒烟账号与专用门店/会员（沿用 agent-square loadtest- 前缀思路）；写路径优先幂等键；每条链路自带 teardown 清理（k6 teardown() 或脚本级 cleanup 场景）；串行依赖的链路用 setup() 准备、exec 分组推进，互不依赖的链路可并行。

4稳定性与 flaky 治理

一次自动重试（仅对网络类错误与 5xx，业务断言失败不重试）；重试后仍失败即判红。连续 N 次同一条链路失败的用例进入「隔离清单」并建单，避免门禁噪声化。

5时长与反馈

service-smoke 目标 < 2 分钟、env-gate < 5 分钟；失败信息直接给出「链路 + 断言 + 实际值 + 追踪 ID」，节点详情页可跳报告。慢链路（跨系统异步）用 MAX_WAIT 轮询终态，不靠 sleep 硬等。

6报告与留痕

统一产出 summary JSON（机器解析，落结果表）+ HTML（人看，归档到对象存储，URL 进 detail_url）。脚本用 group() 划分链路、tags 标注场景与服务，便于后续按服务聚合趋势。

不要做的事：把 UI 断言塞进 k6（k6 是协议层工具，浏览器场景交给已有 UI 自动化）；把冒烟写成「全部接口遍历」（那是回归集，不是冒烟）；让冒烟脚本直接依赖生产数据（prod 只跑只读探活）。

12判定口径与阈值治理 冒烟看通过率，压测看分布；都遵循 no_data=fail

类别判定阈值来源无数据
冒烟（主干）套件内所有必跑链路断言通过；checks 通过率 100%（可配 99% + 白名单）场景文件内联 thresholds + 门禁侧通过率阈值判失败（缺脚本/环境不可达/未执行）
压测（按需）延迟：读 P95 < 500ms / P99 < 1000ms，写 P95 < 800ms；http_req_failed rate<0.01；dropped_iterations == 0P1 固定阈值；P2 与上次发布同场景对比，劣化 > 20% 判失败判失败
目标压力线上实测峰值 × 1.5（从 VictoriaMetrics 取峰值）容量评估会确定—
灰度（prod）5xx 比率 + P95 延迟同时满足AnalysisTemplate 参数分析无数据 → 由 successCondition 显式定义

阈值归属：冒烟由服务 owner 提供、QA 复核；门禁侧通过率阈值走服务树就近覆盖（Application → Module → System → ProductLine → 全局默认），与现有门禁同口径。

13风险、约束与失效模式 门禁被噪声淹没 · 数据污染 · 共享环境互扰 · 版本漏插

风险机理处置
冒烟噪声化（最可能失败的模式）环境不稳 / 数据缺失导致频繁误红，团队开始忽略门禁一次重试 + 隔离清单 + 环境前置检查（env-gate 先跑）；门禁先告警期 2 个迭代再硬阻断
