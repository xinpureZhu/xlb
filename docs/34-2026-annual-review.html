02战役一 · 库存一致性 从「事后补救」到「事前预占」

背景：线上渠道下单后库存未扣减、也未占用，库存仍显示可用——超卖不是体验问题，是履约与口碑问题。这一仗打了四步。

第一步 · 止血（2025-12）：线上商城超卖专项，门店商品库存支持按门店配置超卖策略，先把最痛的门店放开。

第二步 · 换引擎（2025-12 ~ 2026-01）：重写 ERP 实时库存的 Kafka 消费链路——rdkafka 消费、jemalloc 内存分配、至少一次语义、按分区提交 offset、按 company_id 隔离； 同步做门店同步性能优化 2.0 与积分商品库存监听技改。链路从「能消费」变成「可追溯、可重放、不串租户」。

第三步 · 立规矩（2026-07 ~ 2026-08）：牵头「积分商城 + 线上商城预占库存」后端方案（后端负责人，与王杰共同），联合 2 名后端落地： 用户提交订单即校验库存，全部商品预占成功才允许提单，否则返回库存不足；配套「ERP 库存同步支持预占库存」，把预占语义一路打通到库存同步链路。

第四步 · 收口（2026-05）：积分商品库存 Redis 优化，清掉全量缓存中的冗余商品，降低缓存体量与误判面。

库存不是一张表，而是一条横跨 ERP、MQ、Redis、商城的链路。一致性只能靠链路设计，不能靠补丁。

03战役二 · 三方聚合 先造骨架，再长血肉

外卖自研是今年的第二条业务曲线。做法不是「一个平台一套适配」，而是先把「三方怎么接」做成骨架，再按平台长血肉。

骨架 · retail-thirdpart-gateway（P0）：2026-03-26 立项、2026-07-27 结项。本人为后端负责人并完成 MVP——签名、路由、转发、限流，带完整测试； 出站配额与队列模型、回调路由查询与失败记录一并落地。上线后按 4 个缺陷转需求完成二次迭代：路由查询、冗余字段、限流误配、direct 模式仍受限。

血肉 · 三条平台线：

  • 美团闪购：门店、商品、分类、价格库存上下架四模块；订单管理覆盖履约、逆向、查询。
  • 淘宝闪购：门店分类、商品价格与库存对接，复用美团闪购的同步逻辑。
  • 美团团购券：团购券关联秒提商品并同步美团（0630 版本）。

复制 · 万驰：外卖库存同步拉齐最新版本；积分商城与外卖私有化部署，10 个服务的代码任务，把「一套系统服务多租户」跑通。

04战役三 · 商城增长 规则、形态与复制

商城的需求看似零散，实则三条线：规则（兑换怎么算）、形态（卖什么）、复制（怎么低成本复制到新租户）。

  • 规则线：积分商品周/季/年兑换限制、兑换周期与上下架关联、过期退还积分、积分补贴配置与下游接口、批量与定时上下架、库存上限调整。
  • 形态线：虚拟商品二级类型「付费会员卡」、虚拟商品券与券包切换新券接口、积分商品售卖终端区分、积分兑周边品的门店实时库存与可兑换门店。
  • 复制线：旺店通电商商品 4 项（列表、渠道售卖设置、门店同步 MQ、线上商品库新建/编辑）、万驰私有化、商城迁移多租户集群。
  • 存量治理：商城日志脱敏（请求头敏感信息脱敏，BFF 侧同步修复）、线上商品库标准品转多规格取数（排除组合品）、便利店打印机绑定数据跨账套同步。

05战役四 · 平台工程 把重复劳动变成基础设施

平台侧的投入不是「顺手写的脚本」，而是能独立部署、有测试、有手册的服务与工具。全年 330 次提交中，约 200 次落在自建服务与工具仓。

01icc-task · SCRM 任务看板

年度标杆项目。Rust 工作区 5 个 crate：core / api / sync-worker / export-worker / scheduler；覆盖本地查询、定时同步、异步导出、补偿扫描、Redis 限流与任务锁、MySQL 分页与批量 UPSERT、OSS 上传、下载中心对接、组织权限（user-portal + iAuth 双通道）。155 次提交，5 月 18 日 bootstrap，6 月 1 日收口——12 天从零到可交付。

02库存消费者 Rust 化

goods_consumer 承接 ERP 实时库存：worker pool 并发、按分区 offset 提交、毒消息不阻塞分区、Redis 单连接复用、Lua 脚本更新库存；xlb-member-consumer 用 Rust 重写会员积分消费者（4.2k 行）。

03k6 质量门禁

三位一体：调研（25 号）→ 落地手册（31 号）→ 五轨排期（32 号），再到 k6-runner（Go）：K8s Job 跑冒烟、TestRun 跑压测，对外只暴露 POST /v1/runs，测试资产留在各服务仓。

04可观测与巡检

observability-mcp（只读 PromQL / LogsQL / Traces，供 Agent 排障）、logs-monitor（按预设 API 路径统计真实流量覆盖并推飞书）、goods 每日巡检（告警 diff、CronJob 死活、P99 突刺、5xx、MQ 积压、容量趋势一张卡）。

05运营自动化

meituan-test-poi-manage（测试门店到期前自动延期 + 每日结果卡 + k8s 常驻触发）、qoder-stat-menus（macOS 菜单栏配额监控）、wecom-demo 与 worktool 二开（企微机器人；AGP 8.6 / Gradle 8.9 / Kotlin 1.9 / target Android 15）。

06文档与技能

docs/ 33 篇：架构总览、服务清单、10+ 仓深度分析、4 篇故障复盘、k6 三篇、WMS/POS/移动自动化专题；自托管 Mermaid + Cloudflare 部署；7 个可复用 Skill（retag、artifacts 写入、文档部署、每日巡检、RCA、发布验证、交付周报）。

06战役五 · 稳定性 四次复盘，一套方法

10 月的四次线上问题分析，形成了固定打法：先确认失败边（不是整条链路），再用日志/指标/Trace 原文排除法缩小，最后回答「为什么监控没提前发现」。 四篇复盘已归档为 21、28、29、30 号文档。

图 3 · 巡检—复盘—验证的稳定性闭环

四次复盘的共同结论是「发布前置可校验性不足」：目标服务是否存在、跨集群切流是否可见、回调契约是否对齐，都应成为发布门禁而不是事后排查项。 这条结论直接推动了 k6 冒烟接入发布链路与发布后验证 Skill 的建设。

08复盘与远征 把个人效率变成组织能力

01这一年做对了什么

业务需求能从设计走到发版并留下节点证据；库存一致性（超卖 → 预占）形成跨服务方案；三方对接先建网关再铺平台，避免 N 套适配；故障复盘坚持「唯一失败边 + 排除项」，结论可复核。

02还不够的地方

平台工具多为个人侧提效，k6、巡检、MCP 仍跑在个人环境，未平台化与移交；文档产量大但更新靠人，部分文档缺分析基准；预占库存的异常路径（预占超时释放、对账补偿）需要更完整的压测与演练；跨域深度仍偏商城，订单/履约侧参与较少。

03下一年的三件事

① 库存一致性体系化：预占/释放/对账全链路指标化，把「不超卖」变成可观测的 SLA；② 质量门禁落地：k6 按 32 号排期推进到 M3–M5，冒烟成为发布默认门禁；③ 平台能力组织化：巡检与发布验证接入效能平台，7 个 Skill 与 33 篇文档转为团队可维护资产。

04能力补强

补订单/履约域的业务深度；把复盘里的「发布前置校验」建议落成平台能力（目标服务存在性、切流可见性、回调契约校验）；继续用 Rust/Go 承接高并发链路。
